# 项目管理完整功能与业务设计

- 日期：2026-09-12。
- 状态：**完整设计草案，供整体审查；未进入实施**。
- 适用产品：AutoFlow 本地浏览器自动化工作台，Windows/macOS，唯一浏览器运行时 CloakBrowser。
- 推进方式：整个模块先设计和计划，再小步开发，见[已确认推进原则](../../../.ai/decisions/2026-09-12-project-management-complete-design-first.md)。
- 本轮新业务依据：[数据/工作流/环境决定](../../../.ai/decisions/2026-09-12-project-data-workflow-semantics.md)。这些用户已明确的原则优先于先前建议；具体机制及新增便利功能仍标 proposed。
- 总体架构：[总规格](../../superpowers/specs/2026-09-12-project-management-design.md)。历史研究与审查保留为证据，不作为当前冲突规则的优先来源。

## 1. 这份设计交付什么

项目把同一业务的数据、自动化、运行结果和已保存浏览器环境组织在一起。用户可以让多个工作流使用同一批业务数据，明确决定何时改变字段/状态、何时保存并继续使用登录环境。

| 文档 | 要回答的问题 |
|---|---|
| [完整功能与交互结构](functional-structure.md) | 项目和六个页签各做什么，字段、入口、动作、反馈和返回如何组成完整工作路径 |
| [数据与状态规则](data-and-state-rules.md) | 每表状态如何维护，多表怎样取数，何时可以再次使用，结构/记录变化如何避免冲突，Excel/Sheets 怎样保存与同步 |
| [数据传递与模块契约](data-flow-and-contracts.md) | 项目值怎样成为任务输入，参数/变量/输出怎样传递，哪些动作真正写回，部分成功怎样解释 |
| [执行与环境规则](execution-and-environment.md) | 批次、任务、人工与环境怎样转换状态，如何停止/恢复，结束节点如何保存登录态及关联记录，下一次怎样选中 |

这些文件共同构成一个模块设计，彼此不能选择不同规则独立实现。字段、取数和数据写入以数据规格为主；变量传递以传递规格为主；执行终态、保存及环境引用发布以执行规格为主；页面消费这些事实，不另建业务状态源。

## 2. 完整功能结构

```text
项目管理
├── 项目目录：创建、查找、编辑、打开、归档、恢复、删除
└── 项目详情
    ├── 概览：继续工作、活动、需要关注、配置与运行摘要
    ├── 自动化
    │   ├── 基本信息
    │   ├── 输入数据：多表绑定、字段/状态条件、关联、排序、预览
    │   ├── 参数配置
    │   └── 运行设置；进入 Studio 编辑工作流及结束节点
    ├── 运行记录：批次、任务、等待人工、输入与日志、结果与产物
    ├── 统计：范围、口径、指标、趋势、下钻
    ├── 数据
    │   ├── 数据表目录
    │   └── 表内：记录、字段与校验、数据状态、来源、表设置
    └── 环境：运行现场、等待人工、已保存环境、项目默认资源
```

浏览器配置、内核、代理和模型继续由现有全局模块管理。项目引用这些资源；不再新增内核中心、账号专用管理模块或第二套项目资源侧栏。工作区仍是应用设置中的本地数据根，切换项目不会切换工作区或重启服务。

## 3. 用户已明确的业务原则

1. **每表有系统维护的业务状态列。** 状态名称由业务定义，修改由用户或工作流明确动作发起；系统保证身份、版本和持久化。
2. **是否再次使用，由状态和工作流条件决定。** “最终态”不具有系统内置的不可再取含义；不改状态且仍匹配时，记录可再次被同批或其他流程使用。
3. **一个工作流可用多张表。** 同时占用的排他保护继续存在；它不等于“以后不能再用”。
4. **工作流决定数据变化。** 字段、记录、业务状态和字段/列结构通过明确步骤进行增删改查；不在任务结束时隐式修改所有输入。
5. **结束节点可以保留当前环境。** 勾选后要保存登录上下文，并关联相关数据行；对用户是一项完整操作。
6. **后续是否继续使用环境，由工作流设置。** 不根据“看起来是同一个账号”猜测，也不因为全局配置同名就自动共享登录态。

旧源码与 M3 契约已核对：每条记录一个状态或未设置；状态目录初始为空，没有隐式默认。当前采用单值状态，不加多选标签或另一个内置业务状态机。

## 4. 五种事实分别说明

| 事实 | 用户会看到的例子 | 谁能改变 | 不代表什么 |
|---|---|---|---|
| 记录业务状态 | 未设置、待注册、已注册等用户定义值 | 人工明确设置，或工作流状态动作 | 已注册不等于本次任务成功，也不必然不可再用 |
| 记录占用 | 正在被某任务处理 | 运行协调与数据领取 | 占用不会给业务状态偷偷写“处理中” |
| 执行结果 | 运行中、等待人工、收尾中、成功、失败、取消、中断 | 核心执行及受控协调 | 失败不会抹掉已提交的字段/状态 |
| 同步进度 | 本地已保存、待推送、待核验、云端确认、失败 | 来源同步用例 | 本地成功不等于云端成功 |
| 环境处置 | 活动、保存中、已保存、关联待处理、清理失败 | 环境保存/关联/清理用例 | 清理成功不改变失败任务；保留未完整完成不算结束节点成功 |

环境保留是用户明确要求的结束节点动作，因此它的失败会影响该节点和本次执行是否成功；普通临时环境的后续清理、Sheets 异步推送则继续独立展示。这两个情况不能用一条“环境结果永不影响运行”概括。

## 5. 综合业务样例：三张表、两个工作流

这是由已确认规则构造的设计验收样例，不声称用户现实业务一定采用这些名称或步骤。

### 5.1 数据准备

| 表 | 示例业务字段 | 系统业务状态 | 环境关系 |
|---|---|---|---|
| 人员资料 | 人员编号、姓名、资料字段 | 已核验；注册后可保持不变 | 共享资料可不关联某个账号登录环境 |
| 邮箱资料 | 邮箱编号、地址、人员编号 | 待使用 → 已注册，由流程明确改变 | 可选择关联这次注册形成的环境 |
| 账号资料 | 账号编号、人员编号、邮箱编号、结果字段 | 工作流创建时未设置，随后明确设置已注册 | 关联该账号实际保存环境，供后续流程选源 |

“业务状态列”是 AutoFlow 元信息；来源中若也有名叫“状态”的普通字段，两者必须在映射和条件选择中区分。普通来源字段不能覆盖系统状态，也不能因同名被自动当成系统列。

### 5.2 注册工作流

1. 选择人员和邮箱两个具名输入，分别设置字段/状态条件；需要属于同一人员时使用明确业务键关联，不按表的行号凑一组。
2. 在同一领取操作中验证全部必要输入并取得所需占用；记录这一次使用的具体值与版本。
3. 运行网页步骤；计算过程和节点输出保存在本任务独立上下文中。
4. 如需新的业务字段，使用明确新增字段动作，并通过返回的稳定字段引用继续操作；不按列位置猜新增字段。
5. 取得明确业务结果后，向账号表新增记录，记录人员/邮箱业务编号；用明确状态动作更新邮箱和账号状态。人员仍为“已核验”，因此在后续匹配时可再次使用。
6. 结束节点勾选“保留当前环境”，目标选择邮箱输入和本任务新建的账号记录。保存登录上下文并完成这些记录的环境关联；人员资料无需因此绑定到某个账号环境。
7. 执行终态、数据结果、同步与清理分别可查。解除所需占用后，下一项任务重新按条件寻找当前合格记录。

### 5.3 资料更新工作流

1. 从账号表按所需业务状态筛选，明确从当前账号关联选择已保存环境。
2. 根据账号行的人员编号取得相关资料；多个输入指向不同环境时，按工作流显式来源规则决定，不采用输入列表第一项。
3. 恢复保存上下文后进行网页操作，明确更新所需字段和状态。
4. 若业务要求状态保持“已注册”，系统保持该值；释放占用后它仍可再次匹配。有限任务数是执行次数上限，不保证处理同样数量的不同记录。
5. 结束节点再次选择保留时，按明确的保存目标和关联规则保存最新登录态；下一次使用得到已确认发布的内容。

### 5.4 这个样例必须验证的异常

- 人员有数据、邮箱没有：不创建缺邮箱的半任务；与邮箱暂被占用、结构错误分别提示。
- 网页已提交成功，本地账号新增回应丢失：查询同一新增操作，不能再次注册或重复追加账号行。
- 状态已设为“已注册”，后续节点失败：状态保留，失败任务保留；不能暗中把邮箱改回“待使用”。
- 保存环境完成但账号关联冲突：环境保留且操作未完整成功，可处理关联；不能删除唯一保存副本，也不能报完整成功。
- 两任务尝试更新同一保存来源：同一环境身份的占用与保存版本校验阻止静默覆盖。
- 字段结构增加兼容列：允许通过受控操作完成；删除仍被运行使用的字段：明确拒绝并定位依赖。

## 6. 需要整体评审的具体推荐

下面已有明确推荐和配套规则，供审查取舍；不再要求用户先写出一份真实生产流程，设计工作才能继续。

| 主题 | 本稿推荐 | 取舍及适用边界 |
|---|---|---|
| 多表组合 | 每个输入显式声明取数条件；独立取数与显式业务键关联分别说明，同表多用途和可选输入有明确规则 | 支持现有多表需求；不自动按行配对、不做隐式笛卡尔积或通用 JOIN 编辑器 |
| 独立流程用于项目 | 显式关联同一 Studio 文档，不转移所有权；一个流程至多关联一个项目自动化，关联前说明编辑联动 | 删除项目只解绑独立流程；项目中创建的流程按占用检查后删除；本模块不增加复制或所有权转移功能 |
| 状态转换 | 目录声明合法状态；输入条件和状态节点承担业务逻辑，系统检查有效状态与版本 | 不引入另一套允许转换图；必要业务前置条件由工作流表达 |
| 保存来源与持续使用 | 任务使用受控工作副本；结束节点明确保留，发布确认内容并关联所选记录 | 克隆目录不代表新网站身份，源环境和维护会话仍有占用规则 |
| 记录与环境 | 按执行规格定义当前引用、来源记录和历史；多输入不默认猜环境，替换已有不同引用须明确策略 | 一行可能历经多次运行，历史不能因当前关联改变而消失；具体默认属于本稿推荐 |
| Sheets | 保留多项目同源目标，明确同机写协调、映射重叠、公式只读与刷新、发送后核验 | 不承诺跨机器锁，也不把普通云端修改自动覆盖本地值 |
| 失败后的后续业务 | 至少从失败任务准确定位相关记录、当前状态与已发生效果；保持原任务只读 | 后续新批次仍按工作流条件；便捷入口不能偷偷改为每条失败记录强制只做一次 |
| 空白本地表 | 推荐纳入完整模块，复用同一记录/字段/状态能力 | 属此前新增建议；用户确认前保持候选，不为它创建另一种数据库体系 |
| 结果导出 | 推荐提供新文件输出，优先单表 XLSX，按当前选择的字段和业务状态输出 | 属此前新增建议；不覆盖源 Excel，不复制凭据引用内容或内部执行证据到普通结果列 |

多表使用、状态与结束节点的核心要求来自用户确认；具体选择器、流程关联基数、环境关联默认、导出等实现范围仍区分身份。完整性意味着每项都有边界、正向规则和异常答案，而不是把所有建议自动变成已批准需求。

## 7. 架构与组件归属

沿用现有单个本地后端与 SQLite、React 领域组件和统一控件。项目、数据、执行协调和环境是职责边界，不各自搭建服务或数据库。

- **数据应用服务**负责记录/字段/业务状态与对应版本，统一人工和工作流校验；数据与必要同步意图同事务记录。
- **执行核心**负责实际节点运行、变量、尝试和核心结果；通过注入的项目能力调用数据/环境用例，不直接查询项目表。
- **项目运行协调**负责批次条件、领取、输入与任务身份、使用核心启动/取消/查询以及组合概览。
- **环境应用服务**负责实例独占、登录上下文保存、发布、关联协调与清理；具体浏览器和平台动作由既有适配器承接。
- **来源适配器**负责 Excel/Sheets 的实际访问，保持字段映射、稳定身份和同步事实，不决定业务状态流转。
- **前端**复用统一 Button/Input/Select/Combobox/Dialog/Tabs/Table/ScrollArea/反馈；新增领域组件处理条件编辑、记录操作、运行日志和结束节点保留选项。组件先于页面。

设计阶段对齐全部本模块所需 Studio 契约，包含人工继续与结束保留，不把这些推迟到后期才定义。实现按共同依赖表进行：真实保存/基础执行可以先接通，完整项目范围不会因此缩减。主目录 Studio 工作稿由其他任务维护，本轮未修改。

## 8. 整体审查与实施准入

本轮产物是完整模块设计草案。正式逐文件实施计划在整体设计确认后用 `writing-plans` 编写；此时不生成业务代码或先做六页签壳。

整体审查检查以下关系：

1. 功能结构中的每个入口都有明确目的、结果、异常和返回路径；领域细则由配套文档给出，不能仅写“以后处理”。
2. 单表、多表、记录状态不变、状态改变、可选输入、同表多用途、部分缺失都有唯一可解释行为。
3. 初始输入、固定参数、临时变量、写入后返回值及持久数据之间有明确传递方式。
4. 工作流字段/记录操作、人工编辑、同步和结构变更发生竞争时，不会静默丢数据。
5. “保留当前环境”能完整保存并关联，下一工作流确实能选中；保存失败、关联失败、停止和失联有后续处置。
6. 概览/统计、归档/删除、退出/重启都消费同一状态事实，不能仅在正常页面演示中看起来正确。
7. 需求身份、候选便利功能与旧已实现事实分开；未运行的浏览器、Sheets 和跨平台验收不得记完成。

对应文档中的业务验收 ID 将进入实施计划的覆盖表，串联“功能 → 规则 → 前后端任务 → 自动验证 → 真实应用验收”。小步开发只改变任务粒度，完成标准仍覆盖整个已确认模块。
