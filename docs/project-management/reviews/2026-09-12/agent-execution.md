## 结论

这是一份方向基本成立的**待确认总规格**，不是可以直接交给多个子智能体分别开发的实施计划。其“项目层组合、核心独立、按真实能力接入”边界可保留，不需要推倒重做。需要优先修正的是两条有效路线的接入门槛冲突，以及多输入与持久环境复用的可观察业务语义。不能因为文档尚未逐文件列代码、SQL 或每个状态枚举而把它评为不合格；第 5、77、275、314 行已经正确限定了本文粒度。

## 1. [P1] 项目 P4/P5 与当前有效 Studio R9 的接入门槛互相冲突

**方案位置：** 第 15、283–290 行，尤其 P4 只要求真实文档保存，P5 只要求核心网页流程真实运行；第 290 行又明确录制/拾取沿 Studio 专项排期、不隐含在项目管理完成中。

**具体失败场景：** 项目侧已经完成 Excel 本地数据和自动化管理，Studio 也完成当前文档保存和第一条网页流程。项目侧子智能体据 P4/P5 开始接入，而 Studio 子智能体遵守当前有效 `REVERSE_ENGINEERED_DEVELOPMENT_PLAN.md:244`，认为 Manager 组合必须等 R7。R7 又硬依赖 R0–R6（同文件 219 行），其中包含 R6 录制回放。这样最小批次执行仍会被录制、完整基础网页能力、整套独立 Studio 首版交付阻塞，或者两个任务自行选择不同接入时机。

**影响：** 推荐的“双线按最小契约交汇”在现行排期中并没有可共同执行的交汇点。即使接口设计正确，也容易交付大量管理页面后持续等待另一专项。

**最小修正：** 在 P0 同步修订一处双方共同认可的依赖表，将最小“打开/保存关联工作流”接入与完整双窗口/停靠交付分开：前者依赖 Studio R2 的实际能力；最小单次运行接入依赖 R3 的启动/取消/查询/事件及所用节点；完整 R9 的窗口组合仍可后置。对早期执行切片分别保留其实际使用能力的 Windows/macOS 验证，不能用提前接入取消平台门槛。P3 Sheets 则明确为本地数据与执行主链的旁支，不应凭阶段编号成为 P4/P5 的前置条件。

**来源：** 主项目 `docs/automation-studio/PLAN.md:3` 指定逆向计划为当前顺序；`REVERSE_ENGINEERED_DEVELOPMENT_PLAN.md:126–160`（R2/R3）、`:200–219`（R6/R7）、`:242–248`（R9）。这些是同日 working-tree 计划事实，不是已实现状态。

**置信度：高。** 这是文档间明确存在的依赖冲突；精简接入顺序属于审查建议，尚非用户确认的新排期。

## 2. [P1] 多输入已经进入正式能力清单，但“怎样组成一项任务”仍没有正向业务规则

**方案位置：** 第 123 行（具名必要/可选输入，无主表、不按行号、不隐式笛卡尔积）、第 209 行（全部必要输入原子占用）、第 213 行（同批同输入记录默认不重复）及第 217 行（耗尽/暂占分类）。

**具体失败场景：** 一个自动化需要 `person` 和 `email` 两个输入，两张表各有多条匹配记录。方案能告诉实现者不能按行号拼接，却不能确定应当各取排序后的首条、按用户显式条件关联，还是不允许有关系的组合。另一个合法配置是同一张账号表绑定 `sourceAccount` / `targetAccount`：两输入能否引用同一行、要两个不同记录还是应拒绝配置，目前没有定论。可选输入被占用时应当为空继续还是等待，同样会改变输出和批次数。

**影响：** 原子性只能保证“选中的这一组一起占用”，不能保证选中了业务上正确的一组。不同智能体会写出都符合“全有或全无”但数据搭配不同的实现；预览、耗尽判断和同批去重也无法拥有相同验收答案。这是一个会影响运行结果的业务决策，不是以后选哪个 SQL 锁实现的细节。

**最小修正：** 在进入多输入执行切片前，选定并写出一种正向消费规则及 3–4 个具体输入/任务结果样例，至少包含独立队列、多输入同表、可选输入为空/暂占，以及本批已消费的口径。若当前没有真实样例，首个 P5 数据执行闭环只支持一个必要输入，把多输入保留为后续明确能力；不要先做复杂 JOIN/组合框架，也不要在 UI 暗示多输入已经可运行。

**来源：** 方案研究文件 `docs/project-management/research/legacy-core.md:43–44` 明确承认“最终多输入组合算法仍欠执行契约”，`:101` 又列出必要/可选、同表多用途、排序与耗尽的待定项。此发现不是把旧实现当作必须兼容的要求。

**置信度：高。** 文档缺少正向规则可直接核验；推荐先收窄首个执行切片属于实施顺序建议，不取消用户最终多输入能力。

## 3. [P2] 持久环境的“供后续任务复用”还缺从业务输入到具体保存来源的闭环

**方案位置：** 第 125 行的运行设置只有 Profile/代理与运行规模；第 185–190 行承诺显式保存持久环境、后续任务从它创建副本、独占维护以及固定环境 seed；第 285 行把“保存/维护/引用”列为 P6 交付。

**具体失败场景：** 项目保存了账号 A 和账号 B 的两个登录环境，第二个自动化从共享表领取账号 B。当前方案没有说明该输入通过什么稳定引用确定 B 的保存环境；只选择 Profile 只能决定启动参数，无法找到登录会话。若 B 的工作副本在执行中刷新登录状态并显式保存，也没有说明后续任务引用原保存来源还是新保存结果。实现者可能做出可浏览、可重命名的环境目录，却无法正确驱动第二次自动化。

**影响：** 此前提关系直接决定是否恢复正确账号现场，决定 P6 所说的“引用”落在自动化固定设置、具名输入、还是任务资源选择表达式上，也决定输入字段与环境引用保护需要协调到什么程度。它不能仅靠浏览器复制目录的技术验证解决。

**最小修正：** P6 的详细规格先固定一个最小、可验证的来源选择方式：例如自动化显式选择一个持久环境，或具名输入提供一个受校验的稳定环境引用，两者不必同时做。定义工作副本显式保存后是创建新对象并返回引用，还是受控更新某个保存来源；再决定是否/怎样写回业务记录。保留“默认不自动写回共享来源”的现有规则，不据此搭建完整资产版本库。没有这条业务规则前，环境能力可先交付人工保存/维护，但不要把任务复用标完成。

**来源：** 方案本身第 74、125、185–190、285 行；主项目 confirmed 决策 `.ai/decisions/2026-09-12-profile-test-browser.md:10–16` 明确 Profile 是参数模板，不拥有登录会话。实际 `providers/browser/worker.py:57–99` 创建的是临时 context，不能补足持久来源定位语义。

**置信度：中高。** 任务复用入口未在总规格中定义是可核验事实；具体选择方式要在 P6 业务切片设计中确定，因此不阻塞 P1/P2 或纯临时环境的 P5。

## 已检查、但不应误报为架构缺陷的部分

2. **取消、失联与人工现场规则已经包含关键保护。** 第 236 行要求失联先撤销写代次、旧执行确认终止/隔离后才释放；第 237 行要求命令身份与迟到事件保护；第 239 行区分执行名额和现场容量，默认现场上限等于并发数。这样可能导致全部名额都在等人工时批次停止创建新现场，这是明确容量取舍，不是“释放名额”承诺了无限继续。
3. **运行证据不等于产品级版本库，没有必然自相矛盾。** 第 207、221–223 行允许不可变执行输入并排除历史编辑/重放 UI，符合 Studio `PLAN.md:48` 的产品边界。当前 `PLAN.md:177–199` 的 Run 草案尚未容纳这些内容，方案自己承认需要在 P0 对齐。这应是共享契约准入条件，不应被评审者扩大为要求做发布、版本比较或回滚系统。
4. **Studio 自主性保留得合理。** 第 95、211、253 行均不要求 core import 项目表；数据写端口未注入时相关节点明确不可用。无需项目即可编辑并执行通用网页流程，并不意味着没有数据模块也要提供全部项目数据节点。
5. **资源引用与本批固定内容并不冲突。** 静态配置引用使后续批次采用新值，活动批次持有当时有效内容使正在执行的行为稳定，两者可以同时成立。第 203、207 行也已经区分静态引用、活动使用、批次候选集合和按任务解析实际代理；不得把 Profile 或代理组当前可选误认为持久运行已经具备。

## 进入执行计划前的必要验收门槛，而非额外总规格缺陷

P0/P5 的共享契约仍需给出可运行示例，覆盖以下边界即可，不需要先造通用调度框架：

- 同一个 Task 的持久调度身份对应一个核心执行尝试入口：数据占用和 Task 已提交、尚未启动 CoreRun 时进程退出；CoreRun 已接受但返回丢失时重试。二者都应能查询并对账，不能产生第二次网页动作。
- 固定执行内容覆盖该次真正依赖的根流程、边、子流程内容以及非秘密配置。只存 `workflowId`/摘要或每次调用时重新读“当前子流程”不能满足 207/221 行。Studio R4 已规划基础 subflow（逆向计划 168、175 行），因此这不是仅针对未来发布系统的边缘情况。
- 本次运行超时、取消、失败、人工终结、进程中断如何映射到 Task/Batch 聚合；人工继续、超期、浏览器丢失竞争由核心接受一个有效转换；租约/浏览器清理失败不得覆盖任务结果。
- 工作流输入定义、项目输入绑定和实际任务输入之间的版本/校验关系；固定参数和变量的作用域不能靠两个前端页面约定。

当前总规格明确把字段和路由延后到详细规格，以上条件因此适合作为 P0/P5 的完成门槛。不能在这些条件尚未形成共同契约时，仅用“两个智能体都看了总体设计”替代接口评审。

## 优先业务闭环建议

先选一条真实路径验证，而非推进所有页面的完成度：**一个项目、一张 Excel 本地表、一个必要输入、一个固定 Profile、一个可保存的 Studio 网页流程；领取记录后执行真实页面操作，显式写回字段/业务状态，能看到输入与日志，停止并确认回收。** 随后再让第二个自动化在同一表上按更新后的业务条件领取，以证明“多个自动化共享项目数据”这项核心价值。

这个闭环可以依赖 P1/P2 的必要子集、Studio R2/R3 和 P4/P5 的必要子集；Sheets、复杂多输入、统计结果快照、持久环境与人工继续有各自价值，但不是它的技术前置条件。若用户以长期登录环境为首要业务，再把环境单实例保存/维护提前，不能把这个排序偏好伪装成已确认用户要求。

**能否直接交给子智能体实施：不能。** 可先据此修订总路线并制作逐切片规格/实施计划；设计认可后，能够独立交付的切片再并行。不是要求先完成全部系统详细设计后才做任何代码，而是每个被分派的切片应有唯一契约、具体业务示例与验收命令。
