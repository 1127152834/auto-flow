## 1. 专业结论

**总体边界可保留，但还不能直接作为完整实施计划分派开发。** 需要补齐的核心是：一次任务怎样取得正确的一组业务资料，下一次运行怎样继续使用正确的已保存环境，以及项目管理与 Studio 到底在什么阶段接通。另有 Sheets 公式遗漏和跨项目同源收缩需要修正或单独裁定。

现方案已经处理了不少必要的可靠性问题，但它对“系统怎样保护数据”的说明，比对“用户怎样把一件业务持续做完”的说明更完整。继续增加实体、状态和页面，无法替代这几条业务路径。

置信度：**高**（规则缺口、源码用语和跨计划冲突）；用户是否优先需要跨项目同源、结果导出或某一种多输入关联方式，**未知**。本报告中的具体数据量和账号场景是验收反例，不是声称用户已经提供了这些生产业务。

## 2. 用什么产品标准判断

当前应用在设置页把自己称为“**本地浏览器自动化工作台**”，全局入口使用“总览、浏览器配置、代理管理、模型管理、设置”。浏览器配置的主动作是“打开测试浏览器”；已确认 ADR 明确它不保存日常登录会话。项目应沿用这个产品，而不是增加另一套资源中心。[源码与 ADR 摘录](evidence.md)

建议采用这句项目定义：**项目把同一业务的数据、自动化、运行结果和已保存浏览器环境放在一起，方便持续处理这项业务。** 不把项目再称为“工作区”；应用设置中的工作区已经表示本地数据根及服务切换。

对设计的检验顺序应是：

1. 用户能否把待办资料放进项目，并知道哪些已经处理、哪些仍需处理。
2. 一个自动化能否读取正确资料，运行真实浏览器操作，并把明确结果保存给后续自动化使用。
3. 用户能否选择、保存和继续使用同一业务身份的浏览器状态。
4. 失败、等待人工、断网和关闭应用后，能否看懂事实并采取下一步操作。
5. 完成这些事情是否必须理解数据库版本、租约或内部所有权。

这不要求添加账号专用模块、跨机器调度、权限审批或通用数据平台。注册、找回和资料更新只是旧产品定义中的业务例子；新模型仍应通用。

## 3. 需要修正的主要问题

本报告的 P1 表示“阻塞相应功能切片的设计冻结”，不表示已经上线的生产故障；P2 表示应明确纳入、延期或接受限制的产品取舍。不因 P6 有缺口就禁止准备 P1 的独立工作。

### R1 · P1：多输入没有正向取数规则，统一按本批次去重还会截断可复用资料

**位置：**原案第 123、209、213、217 行。

现方案规定不能按行号配对、不能隐式做笛卡尔积，必要输入必须原子占用。这些保护应保留。但它没有说明哪些记录应该组合成一个任务。

两个例子足以暴露差异：账号 A 必须用人员 A 的资料，不能从两个列表各拿第一条；100 条待办可以顺序使用同一个仍可用的执行账号，但第 213 行会在第一个任务后把这个账号从本批候选中排除。后一例即使并发为 1、上限为 100，也会提前结束。

这里实际有三种不同语义：**待处理记录、需要独占但可再次使用的记录、只读参考资料**。它们不必变成三个复杂模块，却不能未经分析都套用“一次消费”。排他占用管同时使用，去重管以后是否还能使用，二者不相同。

旧并发契约明确区分“防同时重复”与“防再次处理”；旧研究也承认多输入组合算法尚未定稿。共享资料与相关记录的具体使用方式仍需当前业务样例裁定，不能直接推导为必须开发通用 JOIN 编辑器。[历史证据](evidence.md)

**建议：**第一条数据执行切片使用一个必要输入，先验证真实闭环；在开放多输入前，以样例确定独立领取、显式关联读取、同表多用途、可选输入为空/占用、可复用记录及耗尽口径。共享资料可由最小的数据读取能力提供，不必一律参与任务消费。所有可复用输入都不能形成耗尽条件时，要求有限任务上限。

**验收：**10 条待办加 1 条可复用记录能按规则生成 10 个任务且不同时占用；A/B 关联资料不会配错；同表两个输入是否允许同一条记录、可选资料暂被占用时是否等待，都有唯一预期答案。输入预览与实际领取采用相同规则。

**置信度：高。** 阻塞多输入切片；不阻塞单必要输入的首条执行链。

### R2 · P1：持久环境缺少“选对、接着用、保存后再找到”的闭环

**位置：**原案第 30、125、185–191、199、207 行。

全局配置是模板，已保存环境才承接登录上下文。当前运行设置和资源链只解释 Profile、代理与并发，尚未说明一条业务记录怎样选择对应的持久环境。

用户为 A、B 保存了两个登录环境后，下一自动化领取 B，必须恢复 B 的环境。只选一个全局浏览器配置不能完成这件事。还必须说明：修改模板指纹后，恢复旧环境采用什么身份；当前模板、已保存上下文和显式覆盖的优先关系是什么。

另一个缺口是后继保存。旧契约和新方案都允许从保存来源创建工作副本，这本身并不错误。但任务更新登录状态后，“保存当前环境”究竟产生新环境、更新原环境，还是更新业务记录的环境引用，目前没有定义。手工独占维护原环境不能自动取回刚才工作副本里的变化。

**建议：**先设计“同一个业务身份连续两次运行”的用例：选择已保存环境 → 建立受控工作副本 → 显式保存 → 下一次明确恢复刚保存的状态。环境来源应能区分新建自配置与使用已保存环境；至少有一种按任务输入定位环境的受校验引用。保存为新环境和更新现有来源必须有清楚语义，可以只先交付一种满足首要场景的方式。

继续保留同目录独占和默认不自动回写。若更新既有来源，应校验源版本/独占资格，保存失败或冲突保留现场；不能最后完成者静默覆盖，也不能把多个目录副本误认为多个独立网站身份。环境固化的指纹不会因模板重置悄悄变化；内核兼容性和代理覆盖须有可见规则。

**验收：**A/B 共用一个模板，B 的任务仍打开 B 的环境；本地测试站点更新会话后，按配置显式保存，第二次运行取得更新后的状态；保存竞争有唯一结果，未成功发布的副本不被误删。Windows/macOS 分别验证自身保存恢复，不承诺跨系统登录态迁移。

**置信度：高。** 阻塞“任务复用持久环境”的冻结；不阻塞临时环境运行或独立保存机制验证。

### R3 · P1：项目与 Studio 的接入计划有真实依赖冲突

**位置：**原案第 283–290 行；主目录 Studio 当前工作稿 `REVERSE_ENGINEERED_DEVELOPMENT_PLAN.md` 第 217–246 行。

项目 P4/P5 希望在真实保存和基础执行就绪时接入，并把录制等交给 Studio 专项排期；Studio 工作稿 R9 却硬依赖 R7，R7 又依赖含录制的 R0–R6 以及完整独立 Studio 交付。这不是接口命名的小问题，而是两个智能体会遵守不同开工条件。

**建议：**双方共同维护一张接入依赖表。当前文档打开/保存可对齐 Studio R2 的真实能力；最小运行可对齐 R3 加该切片确实使用的数据读写、结果和停止能力。这里不能声称 R3 单独已经提供项目数据写回。完整双窗口组合、停靠及 Studio 全部首版仍按专项验收，早期接入也要做本切片实际使用能力的平台验证。

把 Sheets 明确画成支线：Excel 本地数据、参数运行与最小执行不需要先通过 OAuth、远端同步和全套故障恢复。原案只给编号顺序，没有写 P4 必须依赖 P3，故这是需要消除的排期歧义；R9 硬依赖 R7 则是已核验的冲突。

**验收：**双方使用同一工作流标识、保存语义、启动身份和事件；从项目打开、保存、关闭再打开保持内容；启动回应丢失时查询原请求，不重复创建网页动作。实际工作稿尚在其他任务修改，本轮仅记录冲突，未替另一任务改计划。

**置信度：高。** 阻塞并行执行任务的分派，不阻塞独立数据切片。

### R4 · P2：Sheets 单写绑定是产品能力收缩，不能直接当技术必然

**位置：**原案第 173 行。

“一个工作表在本工作区只能绑定一个可写项目”会禁止两个项目分别维护同一张表的不同字段。旧契约不只是泛泛设想共享：它明确记录了同 Spreadsheet 串行定位/写入、跨项目本地状态独立，以及同字段最后成功推送生效的策略。它不证明旧实现已经满足所有竞态，但足以证明“将来有真实共享需求再设计”失去了历史依据。[M5.1 摘录](evidence.md)

**建议：**不要整案默认通过这项限制。优先保留多绑定目标，在同一本地应用内串行协调远端写入，展示映射重叠及来源使用情况；同字段冲突如何处理需重新验收。串行只能防并发操作交错，不能自动解决不同项目本地副本的语义冲突。若当前业务确实不需多项目同源，可以明确延期，不能将其写成必然不支持。

**验收：**两个项目修改不重叠字段，远端两者均保留；修改同字段时结果与所选策略一致；一个项目解绑不会删除另一个依赖的云端身份列。无需全局数据中心或跨机器锁。

**置信度：高**（历史目标和新限制）；当前业务优先级未知。阻塞 Sheets 绑定策略冻结。

### R5 · P1（限 Sheets 切片）：公式结果刷新与公式写保护被绝对规则漏掉

**位置：**原案第 169–171 行。

“入站仅拉取新增记录”遗漏了旧契约对已有记录公式结果的刷新；写保护只写了不覆盖未映射列，也没有保证映射内公式不被普通编辑覆盖。

例如修改数量并推送后，Sheets 已重算合计，但本地因为不是新增记录而一直保留旧合计；后续自动化若读该列，会取得旧值。这是可用固定表重现的正确性问题，不需要假设新的业务模块。

**建议：**区分普通业务字段与云端公式派生值。已有记录普通值仍本地优先，但更新远端定位、公式结果/错误和来源信息；公式字段只读，人工和工作流都不能以普通字段写入覆盖。拉取不会改掉已经领取任务的输入证据，公式刷新与内容版本的关系在数据契约中定义。无需增加通用双向合并或本地公式计算引擎。

**验收：**本地改数量 → 推送并核验 → 拉取后公式结果更新；普通本地字段和业务状态保留；尝试编辑/推送公式被明确拒绝。

**置信度：高。** 主审将两位数据审查中的公式遗漏提升为该切片 P1，因为原案的绝对规则会直接影响任务读取值；不据此阻塞 Excel 工作。

## 5. 产品语言与交互裁定

六个项目页签和自动化四页签都有历史依据，可以保留。真正要避免的是用户每次做业务时需要在六处自行拼接事实。

| 用户可见概念/动作 | 产品含义 | 内部概念的处理 |
|---|---|---|
| 项目 | 同一业务的数据、自动化和环境归属 | 不另称工作区；Workspace 保持设置中的数据根含义 |
| 自动化 / 编辑工作流 | 前者是可重复启动的业务配置，后者是编辑动作步骤 | WorkflowDocument、Studio 窗口会话不再成为另一套必懂的业务对象 |
| 浏览器配置 | 可复用启动参数；仍保留“打开测试浏览器” | Profile 不等于登录环境 |
| 已保存环境 / 使用此环境 | 指向持续使用的浏览器上下文 | PersistentEnvironment 与目录副本版本只在详情/诊断中解释 |
| 运行记录 → 批次 / 任务 | 批次说明一次启动及规模，任务说明一次流程执行 | 保留旧标签即可；不要错误简化为“一任务永远等于一行”，多输入可包含多条记录 |
| 正在处理，暂时无法删除 | 说明受影响对象和用户下一步 | 不直接提示 lease、fencing、generation |
| 数据已被修改，请核对最新内容 | 保留用户草稿，提供比较与重新提交 | 不让用户手填 expectedVersion 或理解 CAS |
| 本地已保存，等待同步 / 正在核验云端结果 | 本地与远端各自真实状态 | 不在本地提交后统一 Toast“全部成功” |
| 停止 / 强制停止 / 继续执行 | 说明是否停止新任务、现有任务与保留现场 | “停止”后的当前任务如何结束应明确；后台协调术语不进入普通操作表单 |

额外两项建议：

- 原案第 130 行让绑定时选择“是否转为项目所有”。建议先验证是否真的需要这个高级选项。项目内新建自然归项目，关联独立流程展示删除影响；若需隔离修改，再明确“复制到项目”或选择受支持的关联方式。不要仅为支撑后台删除策略增加日常所有权判断。单流程只绑定一个自动化也仍属本次建议，不能称为旧产品已确认限制。
- 原案第 149 行的统计一致性目标合理，但“有有效期的结果标识”是候选实现机制。先以数字和下钻结果一致、刷新后成组更新为验收，按真实查询模型选择最小机制；不先建设通用查询快照平台。取消/中断单列、无样本不显示假成功率应保留。

首次使用不必依次配置全部页签。允许从参数流程开始，按需加数据与环境；四页签不是步骤向导。异常入口应落到具体表、任务或环境，返回后保留上下文。运行日志、输入、环境和同步摘要在任务详情中能互相到达，用户无需手抄内部 ID。

## 6. 对实施路线的专业意见

### 先澄清文档级别

被审文件第 275 行已明确是阶段路线；当前 `docs/superpowers/plans/` 没有项目管理逐任务实施计划。不能用缺少逐文件代码和测试命令来否定一份总规格，也不能把 P0–P7 的表格直接交给多个智能体开发。

**建议调整为下面的依赖关系，尚非用户确认的新排期：**

| 交付节点 | 依赖 | 必须展示的真实结果 |
|---|---|---|
| A：业务规则与共享契约 | 本报告对应决定、实际合并基线核对 | 一次任务的输入、环境、启动与结果示例；双方同一依赖表 |
| B：项目与本地数据必要子集 | A 中相关规则、统一控件 | 建项目、导入/维护数据、重启后保留、资源引用保护；前后端一起交付 |
| C：最小真实运行 | Studio 真实保存/基础运行 + 项目参数/输入/写回端口 | 参数单次；再用一张本地表、一个必要输入运行小批次，显式写结果，查看日志、停止、确认回收 |
| D：多自动化共享业务 | C | 第二个自动化能读取第一个明确写出的状态/字段；由真实样例决定扩多输入及复用规则 |
| E：按业务优先级扩展 | B/C 对应能力 | Sheets 按公式/绑定/核验契约接入；持久环境与人工处理按选择/保存/继续契约接入，独立验证可以提前 |
| F：真实概览统计及整体收口 | 有足够真实事件与完成的纵向能力 | 数字可复算、异常可处理、生命周期和真实平台回归 |

如果日常长期登录才是最优先业务，应把单环境连续两次使用的切片提前；当前没有证据替用户决定这一优先级。上表的本地单输入闭环是降低反馈等待的建议，并未取消最终 Sheets、多输入或人工处理。

### 每个切片在分派前必须具备什么

1. 一条具体用户路径和固定输入/预期结果，写清本期未支持行为；不能只有页面名称。
2. 领域契约：写清本切片涉及的归属、状态、版本、操作身份及异常处置。涉及执行时，Task 已保存但未启动、核心已启动但响应丢失这两个边界必须能查询协调，不能再次发起相同网页动作；纯项目 CRUD 不等待执行契约完成。
3. 涉及 Studio 的切片补充共享契约：当前工作流保存、真实执行所用的确定内容、输入/输出、取消/查询/事件；涉及子流程时也固定其实际内容。人工继续依赖核心能力，不由项目页自己修改状态冒充完成。独立 Excel 数据切片不以 Studio 全部接口完成为前提。
4. 确切文件范围和共享文件负责人：后端 domain/application/infrastructure、HTTP/OpenAPI 及生成类型、前端领域组件/页面、迁移与测试。只创建本切片需要的目录。
5. 先复用基础控件和复合模式，再组装业务页；后端、生成类型与真实客户端在同一切片完成，mock 不作为交付。
6. 逐任务给出预期失败场景、验证命令和人工演示。仓库已有 `npm test`、`npm run typecheck`、`npm run lint`、`npm run build`、`npm run openapi:check`；后端已有 pytest、mypy、Ruff 配置。具体测试文件和范围命令应在实施计划读完相关代码后给出，本轮没有运行这些业务检查。
7. 记录实际验收环境与证据。macOS ARM、macOS Intel、Windows x64 分别记录，未运行的平台明确待验收；本地 UI 演示不能抵扣跨平台运行/退出/恢复。

### 多智能体应怎样分工

先由一名契约负责人协调项目与 Studio 的共享边界；按可独立闭环的能力并行：项目/资源引用、本地数据、Studio 保存执行、环境验证。每条线内部仍完成契约、后端、组件、页面和测试，再由独立审查者复核。不要按六个页签各派一个智能体，也不要前后端各自发明 DTO。

共享 OpenAPI 生成文件、数据库迁移汇合点、全局资源删除检查、导航和跨模块状态规则必须有明确负责人。除已约定接口外，避免多个智能体同时修改同一共享文件。

## 7. 保留项、裁定记录及修订优先级

**应保留：**六页签/四页签；全局资源引用；模板与项目环境分离；单 sidecar/本地数据库；Studio 核心独立；原子领取与版本冲突保护；运行结果、业务状态、同步、环境清理分别表达；未知远端结果先核验；失联先撤权、确认旧执行终止或隔离后释放；运行证据不扩展为发布版本库。

| 审查意见 | 主审裁定 |
|---|---|
| 三个智能体都指出多输入未闭环 | 合并为 R1；采纳规则缺口，暂不采纳某一种通用关联编辑器或全输入统一复用开关为既定实现 |
| 环境选源和持续保存两个发现 | 合并为 R2；属于同一跨两次运行用例；不要求推翻旧克隆原则，不引入默认自动回写 |
| Studio 依赖冲突 | 采纳 R3；主目录工作稿仍未等同已实现或已批准，双方需同步裁定 |
| 单写绑定更安全所以应直接接受 | 不接受此推论；R4 保留风险但要求明确产品范围，旧多绑定也仍需真实验收 |
| Sheets 只拉新增可以概括全部入站 | 不接受；R5 保留公式派生值例外并增加验收 |
| 历史失败应该能原任务重跑 | 不接受；C1 只建议可核对地创建后续新任务，是否增加便捷入口仍待定 |
| 空白表、导出属于必须迁移的已确认功能 | 不接受该身份；C2/C3 是有业务价值的新建议，需裁定，不直接开发 |
| 总规格缺少全部字段/精确代码，因此不合格 | 不接受；缺详细实施计划是阶段事实，真正阻塞来自业务答案和跨计划冲突 |
| 四状态链、取消/人工容量、内部运行证据过度设计 | 未找到足够证据；它们保护真实业务，继续保留。只在无实际需求时削减通用框架 |

修订顺序建议：**先完成首个切片实际涉及的业务规则和共同依赖，随即形成该切片的详细计划。** R1 在多输入开放前解决，R2 在任务复用环境前解决，R3 在项目/Studio 分派接入前对齐；R4/R5 在 Sheets 切片冻结前解决。C1–C3 在对应业务切片中明确纳入/延期，不成为所有工作的统一前置条件。没有必要推倒现有导航或重新画全部页面。
