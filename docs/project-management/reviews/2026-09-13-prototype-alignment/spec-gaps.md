## 结论

按 README/manifest 标题核对，91 张当前阅读稿与 2 张同日顺序未明稿中的主要能力，在正式设计中都有对应功能或后续里程碑。但代码级复核发现一项实际交互缺口：原型 `003-record-detail` 的独立记录详情入口没有实现，完整设计也只写了“打开详情保留表筛选”，没有冻结独立路由、详情中的链接动作、状态编辑区及从详情返回列表位置的具体契约。因此不能继续概括为“未发现遗漏”或“PM2实现与原型范围一致”。

原型不能作为倒退业务规则的依据。SQLite 来源、旧消费/占用暗示和可能存在的独立绑定动作，已经被新系统范围或用户明确业务说明取代。PM1/PM2 当前应用只实现项目基础与本地/Excel 数据闭环；自动化、运行、人工、统计、Sheets 和环境页面仍是计划能力，不能因原型存在就声明已经交付。

## 代码级交互差距与设计遗漏

### 阻断：缺少可导航的独立记录详情

- 原型 `PMUI-d3f6c5774ec4`（`003-record-detail`）是独立只读详情页，包含业务字段、链接复制/打开动作，并在右侧提供状态查看/编辑。
- 当前 `DataRecordsTable` 确实有“查看记录”入口，但 `DataTableDetailPage.tsx` 只把 `detailTarget` 打开为 `Modal size="small"`。它列出业务字段并提供“编辑记录/删除记录”，没有独立详情路由、链接复制/打开区，也没有详情内状态编辑区。
- 当前路由 `app/navigation.ts` 只识别 `#/projects/{projectId}/data/{tableId}/{records|fields|statuses|source|settings}`；`ProjectRoute` 没有 datasetGeneration/recordKey 或详情来源字段。刷新、深链、从任务/统计进入某条记录、浏览器前进后退和返回原筛选位置都无法以路由事实表示。
- 状态编辑能力存在，但它是记录表行上的快捷动作，经 `detailIntent="status"` 打开独立 `RecordStatusDialog`；这不等于原型详情页右侧的状态操作。
- 正式设计 DT-02 只写“打开详情保留表筛选”，DT-11 只要求跨任务互查返回位置，没有确定详情路由身份、代次失效处理、链接动作和详情内状态区。实施前需要补一张记录详情交互契约：路由携稳定 RecordRef（包括 datasetGeneration 和 typed recordKey）、来源/返回位置、只读字段与链接投影、状态编辑入口、旧代次/已删除/链接失效结果。否则 PM4/PM7 的任务与统计互查没有稳定落点。

### 已实现但交互载体偏离原型

- 原型 `PMUI-421c549596d2`（`005-record-edit-validation`）是整页编辑表单和固定底部操作栏；当前使用 `RecordEditorDialog` 模态框。类型校验、草稿、CAS、冲突和恢复已经实现，但整页长表单的滚动、固定保存栏、URL恢复和返回详情语义没有对齐。
- 原型 `PMUI-6729305d756d`（`017-record-filter`）是 popover 中应用/取消；当前 `RecordFilterEditor` 是记录页内常驻 section，底部有“取消修改/应用筛选”。服务端查询、草稿与返回状态已经实现，但触发器、关闭/取消和占用页面空间的交互不同。
- 这两项首先是交互对齐决策，不应从图片直接上升为领域规则。用户此次要求重新对齐后，需要由视觉/产品审查明确选择“按原型恢复”或“批准当前载体”，并补相应真实页面验收；在裁定前不能写成一致。

### 标题级范围已有设计覆盖

- 原型的加载、空态、无结果、局部失败、返回恢复和归档只读均已写入各模块“状态补充”或公共导航规则。
- 自动化“更多操作”和删除冲突已由 AU-01/AU-08 及生命周期影响覆盖。
- 运行中的日志、刷新失败、停止/强停、人工检查失败和证据缺失已由 RUN-01 至 RUN-05 与执行契约覆盖。
- 统计口径、刷新到当前和冻结下钻已由 ST-01 至 ST-03 覆盖。
- 字段影响、表删除阻断、资源版本冲突、环境引用失效与清理结果不明均有明确领域影响或恢复契约。
- `PMUI-b3bf4542690d` 是公共控件规范稿；现有设计已经规定统一控件、焦点、键盘、200% 缩放、长内容和浮层滚动，但本次未看原图，不能宣称视觉一致。

## 用户明确更正造成的合法差异

1. **没有消费类型或“本批只用一次”。** 后续是否再次使用记录，只取决于当前业务字段、每表单值业务状态、工作流条件和当时 lease；lease 释放后，同一批次也可以再次匹配。原型中的“记录被占用”只能表示同时排他，不能解释为永久消费或批内历史排除。
2. **任务结果不自动改业务状态。** 工作流节点或人工命令显式写状态；节点后续失败不会回滚已提交状态，也不会根据成功/失败自动映射状态。原型若把运行状态和数据状态并列或近似展示，以正式分离规则为准。
3. **End 的“保留当前环境”是复合动作。** 选择后必须保存登录上下文并关联有写权的相关记录；用户不需要额外配置 Bind 节点。保存成功但关联失败保留环境并显示 `saved_unlinked`/修复路径，不能显示完整成功。
4. **环境来源不靠名称或第一条输入猜测。** 多输入环境冲突必须由工作流显式来源策略解决；后续是否继续使用已保存环境也由工作流配置决定。
5. **SQLite 文件来源不进入新系统。** 旧原型页保留作历史资料；新系统使用受管本地表、Excel 导入和后续 Sheets 绑定。
6. **独立内核入口不恢复。** 原型 README 已明确警告独立内核入口可能与当前业务不同；正式设计通过浏览器配置解析内核，不增加项目内第二套内核中心。

## 已确认的应用外壳差异

2026-09-13用户明确要求“导航按照现状，用顶部导航，不要换成侧边”。保留当前顶部全局导航；原型左侧全局栏不纳入迁移。项目内部的页头、卡片、详情、编辑和浮层仍按原型对齐。此前待协调条目由本次用户确认替代。

## 后续实施门槛

- PM3 只能把参数型批次、自动化管理、真实 Run/日志/截图和临时实例标为可用；数据输入配置可保存和预览，但任何数据型执行必须明确阻断到 PM4。
- PM4 接入记录领取、动态 lease、工作流数据写和占用影响后，才能兑现原型中的运行占用与数据/运行互查。
- PM5 完成人工等待、持久环境和 End 保存关联后，才能兑现人工与环境原型的主要动作。
- PM6 完成 Sheets；PM7 完成概览活动和统计；PM8 完成归档、删除、生命周期和结果不明处置；PM9做跨平台与全模块回归。
- 原型存在不是验收证据。每项能力仍需真实 API、持久事实、错误/恢复路径和真实应用测试；未实现页签继续显示准确不可用状态。
