# AutoFlow 前端交互与展示评审

- 评审对象：github.com/1127152834/auto-flow（提交 ea2cc5b）
- 方法：阅读前端源码（Studio 编辑器、项目输入、项目数据节点、End 节点、自动化输入编辑器、共享组件与样式）；查看仓库内 2026-09-28 的真实界面截图；本地用 Studio 预览模式（Mock 接口）载入一条"邮箱注册"项目流程，分别在 1440×900 和 1280×760 下截图。主应用没有接后端实跑，相关结论来自源码和仓库截图。

## 总体判断

界面的问题和后端是同一个根源：**界面照搬了后端的数据模型，而不是用户的心智模型**。

用户想的是："这个流程要用账号表里的邮箱和密码；成功后把这一行标成已注册；保留登录状态。"

界面让用户做的是：复制 `{PROJECT_INPUTS['<uuid>']['values']['<uuid>']}`；手写带 `recordRef`、`expectedContentRevision`、以字段 UUID 为键的 JSON；在 End 节点里用逗号分隔填写输入 ID。

另外，前端实际上是两个产品拼在一起：主应用是暖色、按令牌设计的一套界面，信息密度偏低；Studio 是从 WebRPA 搬来的另一套，按钮五颜六色、布局拥挤。两边的组件、图标、颜色、交互习惯都不一样。

## 一、工作流如何使用项目数据（最关键）

### 现在的链路

1. **项目 → 数据**：建表、字段、业务状态。
2. **项目 → 自动化 → 输入与参数**：添加输入，逐个选数据表、输入模式、是否必需，展开"字段映射"填别名，展开"筛选与排序"设条件。
3. **Studio（另一个窗口）**：只有从自动化打开时，底部"项目数据"页签才有内容；独立打开时显示"从项目自动化打开工作流，即可查看项目输入"。使用数据有两种方式：点"复制引用"后粘贴，或在输入框里敲 `{` 从下拉里选。
4. **写回数据**：`project_data` 节点。一个下拉里有 14 种操作，包括删除字段、修改字段；要选"所属项目"（带"上一页项目 / 下一页项目"分页），选"授权数据表"，勾选"允许访问的字段"（每个字段旁边显示字段 UUID），最后手写"操作参数（JSON）"。
5. **保留环境**：`project_end` 节点里填"关联输入标识（逗号分隔）"和"新增或已写记录的 RecordRef 列表"。

### 问题

- **依赖方向反了。** 工作流本身不声明"我需要什么数据"，输入由自动化定义，Studio 只能被动发现。用户先在 Studio 里设计流程（最自然的顺序）时，根本没有数据可以引用；换一个自动化绑定同一流程，引用全部失效。
- **到处是内部 ID。** 实测截图：
  - "输入文本"框里显示整串 `{PROJECT_INPUTS['8f3c2a10-…']['values']['c41e9d2a-…']}`；
  - 画布上"记录失败"节点的摘要是 `注册失败 {PROJECT_INPUTS['8f3c2a10…`；
  - 调试时的候选记录表里，"记录"列是记录的 UUID；
  - 数据节点字段列表旁显示字段 UUID；
  - End 节点要求手填输入 ID。

  下拉建议列表里显示的是友好名称"账号 → 邮箱"，但插入到输入框的仍是原始表达式（`variable-input.tsx`），看完一眼就再也读不懂了。
- **实现细节直接暴露给用户。** 例如 `expectedContentRevision`、`recordRef`、"数据集代次"、"授权数据表"、"读取目的"、"表发生重建时需要重新选择"。并发版本号本应由系统自动处理。
- **画布上看不见数据。** 节点摘要只显示选择器（`#email`），不显示它输入的是"账号·邮箱"；看不出哪些节点读数据、哪些写数据；数据从哪里来、流到哪里去，整个画布上无迹可寻。
- **变量提示不看执行顺序。** 下拉会列出所有节点产生的所有变量，包括在当前节点之后才生成的；类型靠逐个节点类型猜。
- **敏感字段靠名字判断。** 用正则 `/password|密码/` 匹配字段别名来决定是否打码，字段叫"口令"就会明文显示。

### 改造方案

1. **工作流声明输入和输出，像函数签名一样。** 例如"账号：邮箱、密码"，输出"注册结果"。自动化只负责把数据表的字段绑定到这些输入上：左右两栏对照，按名字自动匹配，实时显示"当前匹配 128 条"和几行样例数据。
2. **Studio 增加常驻的"数据"侧栏。** 列出各输入的字段和一条样例值；把字段拖进任意输入框，显示为"账号·邮箱"这样的小标签，悬停可以看到样例值。内部仍然存稳定引用，字段改名不影响。
3. **画布节点显示数据标签。** 例如"输入文本：账号·邮箱 → #email"；读数据和写数据的节点有明确标记；选中一个字段时，高亮所有用到它的节点。
4. **把 `project_data` 拆成几个面向任务的节点**，全部用表单填写，版本号由系统处理：
   - "更新当前记录"：字段 → 值；
   - "设置状态"：下拉选状态；
   - "新增记录"：表单；
   - "查询记录"：条件编辑器。

   字段的增删改只放在数据页，从运行节点里去掉。
5. **End 节点改成勾选。** 勾选要关联的输入（用输入名称），外加一个"本任务新增的记录"开关，不再出现任何 ID。
6. **"用这条数据试跑"。** 候选记录按表的主显示字段展示（比如邮箱，而不是 UUID）；试跑时每个节点旁边直接显示它实际用到的值。

## 二、信息架构与交互动线

- **核心闭环要跨两个窗口。** 用户的完整路径是：建数据 → 配自动化 → 设计流程 → 试跑 → 批量运行 → 看结果 → 处理失败行。其中设计和试跑在 Studio 窗口，其余在主窗口，数据绑定又分散在两边。建议把 Studio 做成项目内的一个工作区（仍可弹出为独立窗口），自动化详情页直接嵌入流程预览和"编辑流程"入口。
- **层级太深，页头太重。** 主应用从上到下是：顶部导航（7 项）→ 面包屑 → 项目头（图标 + 标题 + 长描述 + 修改时间，约占 180px 高，每个页签都重复一遍）→ 项目页签 → 页内子页签（数据表 5 个、运行记录 3 个、环境 4 个）→ 任务详情里还有一层页签。截图中内容区从约 330px 的高度才开始。
  - 建议：项目内改为可折叠的左侧导航；项目头压缩成一行（约 56px）；描述只在概览页显示。
- **环境页重复。** 截图中"项目默认资源"既是子页签，又在右侧重复出现一张卡片。
- **总览只是资源计数器。** 显示浏览器配置 0、代理 0、模型 0，下面的"工作入口"和顶部导航完全重复。建议改成运行态总览：正在运行的批次、等待人工、今日失败、成功率、代理健康、磁盘占用。
- **导航分组。** 浏览器配置、代理、模型是"资源"，应收进一个"资源"分组；安卓设备、实验室不应与"项目"并列在一级导航。
- **运行记录缺少实时监控。** 批次和任务都是静态表格。建议提供批次实时视图：
  - 进度条和吞吐量；
  - 每个任务一行：状态、当前节点、耗时、失败原因分类、截图缩略图；
  - 失败按原因分组，一键"重跑失败行 / 跳过这些行"。

  这也是上一份评审里"处理台账"的界面落点。
- **表格可读性差。**
  - 内容区限宽约 1230px，1440 宽的窗口两侧留白，表格里的路径和哈希却被截断；
  - "记录"列与"源文件路径"列内容重复；
  - 行操作混用三种样式：链接"查看"、按钮"编辑"、图标"⋯"；
  - 分页只有"上一页 第 1 页 下一页"，没有总页数、每页条数和跳转；
  - 任务详情里的表格放在半宽卡片中，需要横向滚动。

  建议：数据页全宽；冻结首列；列宽可调；行按状态着色；支持行内编辑；增加"最近运行结果 / 尝试次数"列。
- **信息缺失。** 资源检查表中每一行的"最终采用"都写"已保存的环境策略"，没有说出实际用的是哪个配置、哪个代理。

## 三、Studio 画布与编辑器

- **画布太小。**
  - 1440×900 下，画布约 860×530，只占屏幕约 35%；
  - 1280×760 下，画布约 700×390，右下角的小地图占去一角，实测把右侧分支节点盖住了（1440 宽下同样如此）；
  - 顶部的搜索浮层压住了第一个节点；
  - 底部日志面板即使为空也占 250px。
- **工具栏没有主次。** 两行共约 14 个按钮，至少 5 种颜色：绿色"运行"、绿色"保存"、橙色"打开"、蓝色"导出"、绿色"自动化浏览器"。用户分不出哪个是主操作。
- **节点可读性低。** 节点文字约 10–11px；所有网页类节点都是同一种淡紫色；分支连线上没有"成功 / 失败 / 条件"的文字标签。
- **模块库过大。** 217 个模块放在折叠列表里。实际常用的不到 30 个。
- **配置面板有误导。**
  - 默认值自相矛盾："运行超时后：重试"，但"重试次数"是 0；
  - "超时时间 0 表示不限制"；
  - 上一份评审已确认，这些重试、跳过设置后端根本没有实现。
- **"模块条"视图显示错误。** 实测中，通过错误分支连接的"记录失败"节点被显示在"独立流程"分组下，好像它和主流程没有关系。
- **报错文案看不懂。** 实测运行报错是"请先在打开网页节点明确迁移浏览器配置；旧文档仍可保存或导出。"用户无法据此知道该怎么做。

改造建议：

- 工具栏收成一行：左侧放流程名和保存状态；右侧只放"试跑"和"批量运行"两个主按钮，其余收进"更多"菜单。
- 画布优先：侧栏和底栏可折叠；底栏没有日志时自动收起；小地图默认关闭。
- 节点改成两行：第一行动作，第二行数据标签或目标；状态用小角标显示；文字至少 13px；颜色只按类别用一条细色条区分，其余保持中性。
- 模块库改成命令面板：双击画布或按 `/` 呼出，默认列出常用节点，并支持拼音搜索（已有）。
- 配置面板分"基本"和"高级"，校验错误就地显示在字段旁。

## 四、视觉一致性与设计系统

- **两套设计语言。**
  - 主应用使用 `styles/tokens.css` 的暖色令牌；Studio 使用 1,991 行的 `webrpa.css`。
  - `domains/workflows` 目录下有 1,704 处写死的 Tailwind 调色类（如 `bg-blue-100`、`text-gray-500`），其他业务目录合计只有 131 处。
- **组件重复。** Studio 有自己的一套控件（`workflows/components/controls`：button、select、dialog、checkbox、popover……），与 `shared/components/ui` 重复。
- **图标库混用。** lucide（75 个文件）和 phosphor（83 个文件）同时使用。
- **其他问题。**
  - 没有深色模式；
  - 数据节点配置里的"上一页项目 / 下一页项目"是未加样式的原生按钮；
  - 提示消息堆叠在右上角，会压住页面标题区。

建议：只保留一套令牌和一套组件库，把 Studio 控件迁移到共享组件；只用一套图标；颜色只用于表达状态，类别色只作为细小的色条出现。

## 五、动效

现状：大量 `animate-spin`（53 处）和 `animate-pulse`（21 处）；运行中的节点整个在闪（`ModuleNode.tsx` 里 `animate-pulse`）；有弹跳式的放大动画（`scale-in-bounce`）。好的一面是已经尊重系统的"减少动态效果"设置。

建议：动效用来表达状态和因果关系，而不是装饰。

- **运行时：**
  - 沿当前执行路径的连线做流动效果；
  - 节点只在外圈显示进度，不整体闪烁；
  - 完成的节点淡入一个对勾；
  - 失败时自动把画布移到失败节点，并展开错误原因。
- **批次监控：** 新领取的任务行滑入；进度条平滑增长；计数数字渐变过渡。
- **数据绑定：** 拖动字段标签时，可以放下的输入框高亮；放下后标签轻微弹出确认。
- **通用规则：** 面板过渡 150–200ms、缓出曲线，不用弹跳；加载时用骨架屏（项目里已有组件），少用转圈。

## 六、可读性与文案

- **术语太多。** 界面里直接出现"数据集代次""内容代次""记录槽""读取目的""授权""RecordRef""配置状态不代表执行状态""任务固定当前保存环境的内容代次，执行中不会切换""当前任务还没有可保留的环境实例"等说法。
  - 建议：面向用户的文案只说结果和下一步；专业解释放进悬停提示；建一份术语表统一用词。
- **其他细节。**
  - 耗时显示"0 秒"，应精确到毫秒或显示"不到 1 秒"；
  - 空状态"还没有自动化 / 创建一个自动化，整理你的工作流程"之类写得不错，可以保留。

## 整改优先级

| 优先级 | 内容 |
|---|---|
| P0 | 流程声明输入输出，数据以可读标签显示；写回改为表单；End 改为勾选；隐藏不生效的重试 / 跳过选项；报错显示真实原因和下一步 |
| P1 | 批次实时监控与失败处理；Studio 画布优先布局与单行工具栏；节点显示数据；统一设计系统（令牌、组件、图标） |
| P2 | 运行态总览与导航重组；动效体系；深色模式；术语与文案清理 |
