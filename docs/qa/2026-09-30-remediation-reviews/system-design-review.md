# AutoFlow 系统设计评审

- 评审对象：github.com/1127152834/auto-flow（提交 ea2cc5b，2026-09-30）
- 方法：通读架构与项目管理设计文档；阅读后端执行链路源码（批次调度、数据领取、执行核心、worker、环境、代理、指纹）与 Studio 前端配置；在隔离环境中用仓库自身代码做了 4 个小实验（失败日志、错误分支、领取耗时、节点类型清点）。未运行 CloakBrowser 和完整桌面应用，涉及真实浏览器的结论来自源码推断，已注明。

## 一、我对这个系统的理解

AutoFlow 是一个本地桌面自动化工作台：Electron 外壳 + React 界面 + Python FastAPI 本地服务（sidecar）+ SQLite。核心由两大块组成：

1. **Studio（流程编辑与执行）**：从 WebRPA 迁入的节点式编辑器，后端注册了 220 种节点（网页操作、控制流、变量/列表/字典/数学、AI、SSH、邮件、触发器等），用一个自研图调度器 `WorkflowRuntime` 执行。
2. **项目管理（批量执行）**：项目 = 数据表（本地 / Excel 导入 / Google Sheets 绑定）+ 自动化（绑定一个工作流、输入计划、参数、环境策略、运行策略）+ 批次/任务 + 已保存浏览器环境。

配套能力：CloakBrowser 指纹浏览器（Profile 持有一个 fingerprintSeed）、代理与代理池（含 ProxyPanel 远程换 IP）、模型供应商、凭据库、Android/iOS 模拟器管理。

一次批量执行的真实链路：

批次启动（冻结自动化配置和流程快照）→ 调度循环每次为一个任务"领取"输入记录（加租约、写 Task 和排队中的 CoreRun，同一事务）→ 派发器检查容量 → 为该 Run 启动一个独立 Python worker 子进程 + 一个 CloakBrowser → worker 内 `WorkflowRuntime` 按图执行节点 → 每个事件（日志、节点开始/结束、输出）都经 stdout 发回主服务，主服务写入 SQLite 并提交后才回 ACK，worker 才继续 → 遇到 End 节点可"保留环境"（关闭浏览器、复制用户数据目录为新代次、关联到数据行）→ Run 终态投影到 Task，批次按失败策略决定是否继续领取。

值得肯定的地方：执行代次（fencing）防止失联 worker 回写、操作幂等键、批次启动冻结流程快照、凭据只在 worker 内按需读取、End"保存 + 关联"两阶段并可修复。这些是分布式系统里很专业的做法，应当保留。

## 二、总体判断

设计文档在"一致性、幂等、崩溃恢复、边界竞态"上做到了近乎过度的严谨，但对一个批量自动化工具最核心的三件事——**吞吐、失败处理、身份隔离**——设计得很薄；同时存在"前端能配、文档写了、后端没做"的三方脱节。结果是：系统在小规模、一切顺利时非常"正确"，但一旦规模上来或网站出错，就会慢、会卡、会静默失效，而且很难排查。

仓库在约 19 天内生成了约 7,800 个文档文件（docs 目录 800MB，Markdown 约 6 万行），后端源码约 12.8 万行，但全局并发硬上限只有 2。这说明严谨性投在了错误的地方。

## 三、问题清单（按优先级）

### P0：直接导致"结果不稳定、失败不可解释"

**1. 界面上的"出错重试 / 跳过 / 超时后重试"后端完全没有实现**
- 证据：Studio 配置面板提供"出错时：跳过并继续 / 原地重试 / 回流到上层重试、重试次数、间隔"，以及"超时后：重试 / 跳过"和"重试次数"（`ConfigPanel.tsx` 约 1608–1714 行），画布还会画出红色"错误回流"虚线。后端源码中 `errorPolicy`、`retryCount`、`timeoutAction` 零引用；执行核心里没有任何节点重试逻辑。
- 后果：用户以为设置了重试，实际上第一次失败就失败。这是最危险的一类问题——静默失效。
- 整改：在 `WorkflowRuntime` 实现节点级错误策略（重试次数、退避、回流目标、耗尽后动作），并区分"可安全重试"（读取、等待、导航）和"可能产生外部副作用"（提交表单、下单）两类节点；实现之前先把这些选项从界面隐藏。另外，后端对节点配置应做 schema 校验，遇到不认识的配置键要报警，防止以后再出现"前端有、后端无"。

**2. 批量运行时，节点失败的真实原因被丢弃**
- 证据：`providers/browser/project_graph.py:424` 把失败统一改写为"工作流节点执行失败"。实验：用项目执行器跑一个解析非法 JSON 的节点，运行日志只有"开始执行节点 / 工作流节点执行失败"，没有任何具体原因。Studio 的 worker（`workflow_worker.py`）会保留真实错误信息——同一个流程在 Studio 调试能看到原因，放进批次就看不到。
- 后果：批量任务失败后几乎无法排查。
- 整改：日志和 nodeAttempt 事件中携带原始错误信息（含凭据派生值时由已有的 `_reported_result` 脱敏即可），并附带错误分类（元素未找到 / 超时 / 网络 / 代理 / 业务断言）。

**3. 用错误分支"处理过"的失败，整个 Run 仍然记为失败**
- 证据：`application/workflows/runtime.py:333` 节点失败时先 `_remember_failure`，再执行错误分支，且之后从不清除；Run 成功与否取决于 `failed_result is None`。仓库测试 `test_failure_dispatches_error_edge_before_runtime_reports_failure` 明确断言了这一行为（沿用 WebRPA 语义）。实验：错误分支已执行并设置了变量，Run 结果仍是 failed。
- 后果：用户写了"登录失败 → 标记这条账号为'登录失败' → 结束"这样的正确流程，任务依然算失败；而批次默认策略是"任务失败即停止领取"，一条账号出错就让整批停下。
- 整改：区分三种结果——技术失败（未处理的异常）、业务失败（流程显式判定，例如 End 节点带结果"失败"）、已处理并成功完成。有错误分支接住的失败不应计为 Run 失败；批次的"失败后停止"只针对未处理的技术失败，或达到失败率阈值时才触发。

**4. 失败记录会被反复领取，导致死循环或饿死**
- 证据：设计文档明确规定"没有批内已消费集合，失败历史也不加入排除条件"（执行规格 §4.1、验收样例 XE-A21/A22）；领取时按固定顺序排序（默认按记录键）。
- 后果：若排在最前的一条记录每次都失败且不改状态——开启"失败后继续"并选"不限次数"时，批次会永远在这一条上循环；选有限 N 次时，N 次机会全部耗在这一条上，后面的记录一条也处理不到。想实现"每行处理一次、失败最多重试 3 次、仍失败就标记跳过"这种最常见的批处理模式，用户必须自己在流程开头和结尾写状态节点，而流程在两者之间崩溃时记录会永远卡在"处理中"。
- 整改：引入"处理台账"——按（自动化 × 记录）记录尝试次数、最后结果、最后错误、下次可领取时间。领取模式默认"未成功处理过的记录"，并支持重试预算、退避、超过预算自动隔离（进入"待人工"列表）。台账和业务状态列分开：业务状态由用户定义，处理台账由系统维护。设计文档里"是否再次使用只由业务状态决定"的原则适合少数"循环复用"场景，应作为可选模式，而不是唯一模式。

**5. 并发硬上限为 2，且人工等待占用执行名额**
- 证据：`dispatcher.py:133` 只接受容量 1 或 2，`bootstrap/workflows.py:566,599` 写死为 2；自动化配置却允许并发 1–100，超出部分被静默截断。任务进入"等待人工"后，其 owner 仍留在派发器中（只在 `_clear_owner` 时移除），计入容量——这与设计文档"人工等待释放自动执行名额"相矛盾。
- 后果：用户设置并发 20，实际只跑 2；两个任务同时等人工时，整台机器的所有批次全部停住。
- 整改：容量改为按机器资源（CPU、内存、浏览器数）配置并在界面上如实显示；"执行名额"和"存活浏览器数"分开计数，人工等待只占后者；多批次之间做公平调度（目前按创建顺序串行推进，先建的批次可能长期占满名额）。

### P1：效率与可扩展性

**6. 每领取一个任务都要全表扫描，且阻塞整个服务**
- 证据：`project_claims.py` 每次领取最多加载 10,001 整行（含全部字段 JSON），用 Python 自定义函数和排序规则在 SQLite 里排序，然后才在 Python 中按条件过滤（约 532 行，过滤发生在截断之后）；每次还要加载全库所有活跃租约，并逐行解析租约身份（Sheets 表每行还要额外查询）。调度器在 asyncio 事件循环里同步调用领取（`scheduler.py:418`），没有放到线程。
- 实测（本容器，仓库自身代码）：2,000 行表单次领取约 0.5 秒，10,000 行约 2.0–2.6 秒。
- 后果：处理一万行数据时，光"领取"就要累计数小时；每次领取期间事件循环被阻塞 2 秒以上，所有 API、界面推送和正在运行任务的事件确认一起卡住。
- 整改：把筛选和排序下推到 SQL（为常用筛选字段建生成列或索引，业务状态本来就是独立列）；用"预取候选队列 + 条件更新抢占"的方式领取，一次查询服务多个任务；所有同步数据库操作移到线程执行，或改为单写线程 + 队列。

**7. 每条日志都同步落库并等待确认**
- 证据：worker 发出的每个事件都要等主服务 `_commit_event` 提交 SQLite 事务后回 ACK 才继续执行（`dispatcher.py` 约 782 行）；数据库未开启 WAL，未设 `busy_timeout`，同一文件被多个引擎打开，代码中 9 处单独处理"database is locked"。
- 后果：一个节点至少产生 4–5 个事件；1,000 次循环 × 5 个节点就是上万次同步提交，执行速度被磁盘 fsync 限制，并发时锁冲突概率高。
- 整改：开启 WAL + `synchronous=NORMAL` + `busy_timeout`；只有"改变状态的事件"（数据写入、End、终态）需要同步确认，普通日志和进度批量异步写入；统一使用一个数据库引擎。

**8. 每个任务都冷启动，环境每次整体复制并哈希**
- 证据：每个 Run 启动一个新的 Python 解释器子进程（启动超时 90 秒）和一个新浏览器，任务之间不复用；恢复已保存环境时，对整个浏览器用户目录做 `copytree`，并对每个文件做全量 SHA-256 校验（`environment_store.py` 38、62、156 行）；保存时再复制一遍、再全量哈希；缓存目录（Cache、Code Cache、GPUCache 等）同样复制；旧代次目录没有找到清理逻辑。worker 的 stderr 直接丢弃（`project_workflow_worker.py:171`），启动失败时无从排查。
- 后果：几百 MB 的浏览器配置每个任务要读写数次，磁盘占用只增不减；对"只是换一行数据抓一个页面"的任务，冷启动开销远大于实际工作。
- 整改：worker 进程池复用；同一身份的连续任务复用浏览器上下文（在流程或自动化上标注"可复用会话"）；复制时排除缓存目录，改用硬链接或增量同步；哈希改为基于文件清单（路径 + 大小 + 修改时间），只对关键文件（Cookies、Local Storage）做内容哈希；保留最近 N 个代次；worker stderr 写入按 Run 归档的日志文件。

### P1：身份、指纹、代理——"配套能力"没有真正服务于批量自动化

**9. 指纹、代理、账号三者没有绑定成一个"身份"**
- 指纹：种子挂在 Profile 上（`profiles/service.py:30`，范围只有 10000–99999）。"从配置新建"环境时，同一批次里的所有任务使用同一个 Profile，也就是**同一个指纹**——批量处理 100 个账号，网站看到的是同一台设备。种子空间只有 9 万个：1,000 个 Profile 时出现重复种子的概率约 99.6%，300 个时约 39%。（若 CloakBrowser 本身只接受 5 位种子，至少要在分配时保证唯一。）
- 代理：代理池按 Run 轮询分配成员，不和环境或账号绑定。一个已保存的登录环境每次运行可能换一个出口 IP；如果 Profile 开启了 geoip，时区也会随之变化。
- 失败分类：代理不可用、浏览器启动失败被当作普通任务失败处理——会占用记录、触发"失败后停止"。
- 整改：把"身份"做成一等对象：身份 = 指纹种子 + 固定或粘性代理 + 已保存环境 + 时区/语言，通常对应一条账号记录。新建身份时自动生成不重复的种子；代理按身份粘性分配；启动前校验 IP 地理位置与时区、语言是否一致；把基础设施失败（代理、浏览器、网络）和业务失败分开——基础设施失败自动换资源重试，不消耗记录的重试预算，也不触发批次停止。

### P1：数据流转的逻辑问题

**10. 三套数据概念并存，引用方式脆弱**
- 流程变量是一个扁平的全局字典；节点输出写到哪个变量名，靠 `project_graph.py` 里按节点类型逐个猜配置键（resultVariable / variableName / saveResult / saveToVariable…），没有统一的输出契约。
- 此外还有 WebRPA 的运行内存表（table_* 节点）和项目数据表，两者互不相通。
- 项目输入在节点里的写法是 `{PROJECT_INPUTS['<uuid>']['values']['<uuid>']}` 这样的字符串模板，靠正则扫描校验；写在 JS/Python 脚本里的引用不会被校验。
- 工作流运行时可以执行 addField / modifyField / deleteField，也就是在并发任务中修改表结构。
- 整改：节点声明带类型的输入/输出端口，输出统一落到"节点名.输出名"；引用使用可读别名，编辑器负责解析到 ID；表结构变更只允许在设计期或维护操作中进行，运行时只写数据；内存表并入项目数据（或明确定位为临时表，结束时可一键导出为结果表）。

**11. 一行坏数据让整个输入失效**
- 证据：`project_claims.py` 约 555 行，任一候选行解析租约身份出错（例如 Sheets 某行未通过最近一次校验），整个输入被判为"配置错误"，批次进入收尾并以失败结束。
- 整改：逐行隔离，跳过并标记问题行，继续领取其他行；只有表级问题（表不存在、结构失效）才判为配置错误。

**12. 业务状态列被多个自动化共享**
- 每张表只有一个单值业务状态。当"注册"和"资料更新"两个自动化都用状态来控制领取时，彼此的状态语义会相互干扰。第 4 条的处理台账是按自动化隔离的，可以解决这一耦合。

### P2：结构与范围

**13. 两套执行栈**
- Studio 运行走 `WorkflowRunCoordinator` + `workflow_worker.py`（2,143 行），项目运行走 `WorkflowRunDispatcher` + `project_workflow_worker.py`，数据库里也是两套运行表，容量各自计算。第 2 条"调试能看到错误、批量看不到"就是这种分叉的直接结果。
- 整改：只保留一个执行引擎，Studio 调试 = 带调试标志的单任务项目运行。

**14. 节点目录过度膨胀，核心原语反而缺失**
- 220 种节点里约 80 个是纯计算/数据变换（math_factorial、rgb_to_cmyk、hex_to_cmyk、stat_variance、list_cartesian_product…），应该由一门表达式语言替代；还有 hotkey/face/sound/gesture 触发器、shutdown_system、lock_screen、打印机、局域网共享等，与"网页批量自动化"无关，在并发批次里甚至是危险的。
- 反过来，网页自动化缺少"按键"节点：键盘类别被整体排除，但录制器遇到按键（例如搜索框回车）会生成 `keyboard_action` 节点（`recordingGeneration.ts:177`），工具栏随后因包含已排除节点而拒绝运行——**任何录到回车键的流程都跑不起来**。
- 整改：精简为 40–60 个核心节点 + 表达式/脚本；补上按键、Cookie/Storage 读写、请求拦截等网页原语；录制器只生成后端支持的节点。

**15. 项目批次不能定时或由事件触发**
- 定时任务只支持独立工作流（`schedules.py` 调用的是 workflow_id），项目自动化没有调度入口；设计文档明确"不在本文增加调度产品"。"每天早上处理新增数据"这种最常见的批量需求无法实现。
- 整改：让定时器和 Webhook 调用同一个"启动批次"用例即可，幂等和冻结机制已经具备。

**16. 范围与工程方法**
- Android/iOS 模拟器管理约 1.5 万行、Google Sheets 双向同步约 4,700 行，而批量核心吞吐被限制在 2。项目自己的修复台账关注的都是边界一致性问题，上面这些主干问题都不在其中。
- 整改：先定义产品级指标——每小时完成任务数、任务成功率、失败可解释率、单任务资源成本——并建立一个"黄金场景"基准（例如 1 万行账号表 × 登录 × 抓取 × 回写，随机注入代理失效和页面超时），所有改动以这个基准的数据为准。设计文档应从"状态机穷举"转向"指标与取舍"。

## 四、整改路线

| 阶段 | 目标 | 内容 |
|---|---|---|
| 第 1 阶段（止血） | 消除静默失效 | 实现或隐藏节点错误策略、重试、超时动作；批量日志带真实错误与分类；明确"已处理失败"语义；补按键节点、修录制器；容量可配置且人工等待不占执行名额；领取移出事件循环；SQLite 开 WAL + busy_timeout |
| 第 2 阶段（可靠） | 批量结果可预期 | 处理台账 + 重试预算 + 自动隔离；失败分类（基础设施 / 业务 / 未知副作用）；坏行隔离；批次失败按阈值而非"一次即停"；项目批次支持定时与 Webhook |
| 第 3 阶段（高效） | 可扩展到万级任务 | 筛选与排序下推 SQL、预取候选队列；事件分级异步落库；worker 进程池、浏览器会话复用；环境存储瘦身与代次清理 |
| 第 4 阶段（身份） | 配套能力真正服务于自动化 | 身份一等对象（种子 + 粘性代理 + 环境 + 时区/语言）；启动前一致性校验；代理健康预检与自动替换 |
| 第 5 阶段（收敛） | 降低维护成本 | 合并两套执行栈；节点输入/输出契约与可读引用；节点目录精简 + 表达式语言；冻结非核心范围（Android/iOS、桌面触发器等） |

## 五、验证边界

- 已实测：批量执行失败日志丢失原因、错误分支处理后 Run 仍失败、单次领取耗时（本容器 2,000 行约 0.5 秒，10,000 行约 2.0–2.6 秒）、生产注册表 220 种节点。
- 源码确认但未实跑：并发上限 2、人工等待占用容量、错误策略与重试未实现、录制器生成被排除节点、指纹种子按 Profile 共享、代理池非粘性、环境整目录复制和全量哈希、事件逐条同步提交。
- 基于设计文档与源码的推断：失败记录的死循环/饿死（排序固定 + 无排除机制，文档验收样例 XE-A21/A22 明确了这一语义）。
- 未验证：真实 CloakBrowser 下的启动耗时、环境目录实际大小、Windows/macOS 平台差异。
