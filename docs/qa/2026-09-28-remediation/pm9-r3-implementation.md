## 所有权与不变量

| 事实 | 唯一所有者 | 本次执行链使用方式 |
| --- | --- | --- |
| 正式项目记录、状态、字段、行版本 | 现有 project_data 仓储与能力用例 | worker 只持有宿主颁发的固定作用域，通过原幂等 commandId 请求 |
| 运行内存表 | ExecutionContext | 不自动转成项目数据库；需要正式写入时显式项目数据节点 |
| Task 输入快照、领取/租约、CoreRun 代次 | 现有 project_runs + workflow_runtime SQLite 事务 | 读取事实冻结，写入逐次检查代次，旧 worker 不得继续写 |
| 浏览器工作副本、持久环境 generation、保存/关联/End ledger | EnvironmentService 与现有 store/repository | 先确认真实 browser/worker 退出，再保存/关联；未知结果保留核验责任 |
| 人工项与执行检查点 | 当前 CoreRun 持久事实及现有人工命令 | 必须同时有可续接状态和 CAS 版本，不能只生成一个 UI 摘要 |
| 运行日志、节点访问和产物索引 | 已确认的核心事件与产物仓储 | 节点推进等待宿主提交 ACK；UI 从持久接口恢复 |

## 推进顺序与兼容要求

1. 先闭合生产 End：在现有固定 worker 协议/事件确认上登记可审计的 End 意图；宿主只从当前 Task/Run/环境实例推导身份，冻结节点约束授权目标。worker 清理确认后复用 `EnvironmentService.end`。保留原操作键核验，浏览器退出未知、保存未知、保存但未关联均不得推进成功终态。
2. End 的最终化和取消/强停必须共用已有控制所有权；不能释放资源租约后再保存，也不能仅执行前比较一次 executionGeneration 就允许后台线程继续。线程取消必须等待实际工作收敛。重启区分已确认关闭后的可恢复最终化与仍可能存在旧 worker 的未知现场。
3. 人工续接在共享 WorkflowRuntime 内建立明确的持久检查点格式和恢复校验，覆盖 ready/pending/executed、循环状态、嵌套调用、变量/内存表、冻结内容身份及当前检查点修订。只有在没有未确认节点副作用的边界才提交可恢复检查点。不得通过重新运行完成节点来重建现场，不得把敏感派生值明文存入事件/检查点。
4. 复用现有 manual 的请求/查询/CAS/到期入口，令响应与真实 CoreRun 事务一致；修复 finish_manual 在重试时生成新 End UUID 的问题。恢复、终结、取消和过期必须互斥，重启保留有效 waiting_manual，UI 刷新从持久事实读取。
5. 前端只补正式节点配置和现有项目页面缺少的绑定/诊断；新增公共 DTO 时先更新后端再生成唯一客户端。现有旧流程默认行为不变，缺能力明确拒绝。

## 必须执行的验收

- 真实本地登录站 + 实际仓库输入 + 生产 worker/CloakBrowser + 隔离 SQLite：领取→浏览器→新记录→状态→End 保存并关联新记录→另一运行复用登录。
- 人工检查点保存后销毁应用对象/进程，用同一隔离工作区重建；继续后已完成网页副作用计数仍为 1，节点访问身份/后续数据写入可核对。
- 重复命令、丢回执、并发人工决定、记录/环境版本冲突、取消、强停、过期、崩溃；旧代次不得修改项目数据或发布环境 generation。
- 并行/循环/嵌套检查点不满足恢复能力时必须在副作用前明确拒绝，不能静默降级为从头执行；完整支持情况按具体用例列账，未通过不算完成。
- 打包应用实际保存/重载/重启/人工入口与本次进程和目录清理，单独记录。当前尚未执行，不作为通过证据。

## 发现的规格冲突与待裁定差异（2026-09-28）

原完整设计 `docs/project-management/design/execution-and-environment.md` 第 175、183、359 行要求：人工继续必须保持同一可用页面；需要关闭唯一浏览器的保存动作视为保存并结束；应用重启后已派发无可靠终态的 Run 中断，不继续旧网页流程。PM9 2026-09-20 规格要求持久检查点继续但没有明确推翻这些现场条件。本次用户要求“应用重启后继续恢复”，如果包括已关闭浏览器的旧 Run，就改变了原有恢复语义，不能通过修改状态名称掩盖。

建议增量契约：仅用户显式配置的“可持久恢复检查点”允许重启后由人工确认继续；普通暂停、未知副作用、检查点未确认以及丢失的现场仍按 interrupted/核验处理。恢复同一 Run/Task，递增执行代次与检查点修订，旧执行授权永久失效；已提交节点不重跑。检查点提交必须在受支持的安全边界、没有未确认并发动作时完成，持有同一资源及数据占用。保存执行位置/控制栈/变量/内存表、冻结内容摘要、环境身份和页面恢复条件；敏感值只能通过现有凭据能力引用或工作区隔离的加密状态保存，不能写事件明文。浏览器 Cookie/存储可恢复不代表 DOM、JS 内存、打开文件或外部连接可恢复；不满足明确恢复条件的节点组合在执行前拒绝持久恢复准入，并给出缺失能力。

兼容性：已有工作流默认不增加恢复资格，不改变 interrupted 的不可逆终态，不自动重启批次，不迁移旧人工项为可执行检查点。既有普通人工现场继续和“保存并结束”保留。新检查点采用新增版本化持久事实与公共能力标记，旧客户端读到未识别恢复状态时禁用继续并要求刷新；不得猜测起点。

实施顺序：先完成不依赖此裁定的 End 最终化与现有人工命令错误/幂等修复；裁定后实现检查点格式、原子接纳和运行代次转换，再接共享 Runtime 的恢复入口及 UI；最后以真实 worker/浏览器/SQLite 重启验证一次副作用、失效代次、检查点损坏、过期、取消及资源清理。逐类图结构有正向恢复证据后才开放，不用新执行器或回放完成节点实现恢复。

此差异尚待用户裁定，不能将建议记录为已批准或已交付。
