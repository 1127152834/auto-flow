# M3 Task 1 + Task 2：领取基准与 SQL 下推（步骤级与结果）

- 日期：2026-10-03；状态：confirmed（本机 Windows 测量）
- 规格：[M3 规格](../specs/2026-09-30-remediation-m3-throughput.md) R3-01、R3-02；AC3-01、AC3-07

## 实施前核实

- 领取每次最多读 1 万行 ORM 对象，SQLite 用 Python 自定义函数/排序规则对整表排序；筛选在 Python 中逐行判断；
  租约和台账每次全量加载；每个候选行都构建并冻结候选对象。10 万行一次领取 1.4–1.6 s，字段排序 14 s。
- 活动租约的部分唯一索引早已存在（`uq_project_record_leases_active_key`），R3-02 的抢占约束不需新建。

## 做了什么

1. 基准（Task 1）：`bench_claims` 改为 6 位编号数据，四个方案各取 5 次中位数：记录键顺序、创建时间顺序、
   字段前缀筛选（命中末尾 100 行）、字段排序（标为全扫描）；测"按调度器页大小选取 + 提交前复核"。
   CI 增加 10 万行 `--budget-ms 20`，只对走索引的方案设预算，全扫描方案照实记录。
2. 筛选下推 `infrastructure/database/project_filter_sql.py`：状态与文本/数字/布尔字段比较翻译为 SQL；
   只允许"不比领域判断更严"，`exact` 标记决定能否取反；SQL NULL 统一视为假。日期比较不翻译（扩大为全部行）。
   Python `matches` 仍对每个候选复核。
3. 排序下推：系统字段（记录键/创建/更新时间）用表达式部分索引（迁移 `rm3_claim_indexes`，大表只建索引不重建）；
   文本/数字/布尔字段与状态排序翻译为 SQL（C 层排序，无索引）；日期字段仍用原 Python 排序规则。
4. 台账门禁下推：本地表在 SQL 排除当前模式下永远不可领的处理记录；按时间的等待仍由领域判断。Sheets 表不下推。
5. 候选页：独立且无其他输入依赖的主输入每次只取 并发×4（至少 64）行；被依赖的输入保持原页大小，关联匹配不变；
   续扫偏移按各自页大小推进。租约与台账只查本页的键。
6. 自动化运行提示（非阻断 `notices`）：按字段筛选或排序的输入提示"数据很多时每次领取需要逐行检查，会慢一些"。

## 结果（10 万行，本机 Windows，5 次中位数，ms）

| 方案 | 改前 | 改后 |
|---|---|---|
| 记录键顺序（索引） | 1556 | 4.8 |
| 创建时间顺序（索引） | 1428 | 6.6 |
| 字段前缀筛选（无索引扫描） | 962，且首页 1 万行内未命中，需续扫约 10 轮 | 142，一次命中 |
| 字段排序（无索引，C 层排序） | 14291 | 272 |

1 万行：记录键 761→4.6，创建时间 808→5.0，字段筛选 316→27.5，字段排序 1061→295。

## 正确性证据

- `test_filter_sql.py`：400 个随机筛选 × 300 行混合类型，SQL 结果 ⊇ 领域结果，exact 时逐行相等。
- `test_claim_order_sql.py`：120 组随机多键排序（含缺失/错类型/状态/三种键类型）与原排序规则逐行一致。
- `test_claim_randomized.py`（AC3-07）：26 个场景、随机筛选/排序/并发，合计 1052 次真实调度器领取，
  每条匹配行恰好一次、不匹配行从不领取、批次在有界轮数内结束。
- 原有领取、续扫、台账、调试输入、Sheets 领取测试通过；一条续扫测试改为验证"下推后首页即命中"。
