# 安卓四图精确还原实施计划

日期：2026-09-13；状态：**proposed，待用户审阅；未开始业务实施**。
输入：用户本轮附上的R1–R4；[规格说明书](../specs/2026-09-13-android-prototype-exact-design.md)。
目标：先把逐图还原标准固定，再按功能切片补齐真实行为。输出为正式Mac模块、四图视觉证据、真实设备验证记录和可运行应用；本轮只交付这份计划与规格。

## 1. 执行边界

- 已有代码起点为 `codex/android-workflow-handoff@cc2c9bb`，M4已汇合；主工作区仍有未提交M5重叠改动。保持隔离工作树，实施时读取实际提交状态后集成；不得覆盖主工作区、改写旧迁移、强制重置或合并未提交文件。
- 本规格获得用户确认后才编写业务代码。D1（内嵌操作/只用原生窗口）在输入与传输切片前定案；规格暂以原图内嵌操作为默认设计，未把缺省当作确认。
- 现有基础控件、服务、M4/M5调度和数据库优先复用；不另建独立演示站点、第二个工作流引擎、Redis队列或整套新UI库。Ponytail仅用于减少重复实现，不能删用户明确要求的控件和功能。
- 本轮不重新创作四个页面，不先做“优化版”；只对无原图的支撑弹窗/标签内容补组件样例。未在原图出现的扩展，不抢占四图主区域。
- 不承诺一次性完成后才给用户看。每张页面先给相同状态的叠图证据，再验证真实功能；中间状态标部分完成，不能以一张看板宣布四页完成。

## 4. 三个必须先解决的技术关口

### G1：两台设备并发

当前全局active_slot、VM锁与单实例runtime需要协调调整。先梳理所有busy/active/recovery/stop调用点，在同一服务中建立按设备的上下文，保留跨工作区身份锁；数据库租约使用条件写/唯一约束避免并发分配。VM预算锁仅覆盖预算预留与生命周期写操作。测试同时启动两台不同设备、同设备两个竞争请求、停止A不影响B、跨工作区冲突，以及浏览器M5原有预算。

不能仅删除busy判断：没有所有权隔离就放开并发将导致控制发错设备。也不能维持全局串行后用假进度填出R1第二张占用卡。

### G2：连续画面和中文输入

建立最小实机验证：一台真实Android、一个嵌入viewport，完成画面解码/帧元数据、点击滑动、中文换行、失焦释放、屏幕旋转。具体scrcpy桥接/解码方式在本机验证后写ADR；不能提前声称已有工具原生支持Electron嵌入。新增依赖固定版本、许可证、Mac包内路径；禁止运行时从任意URL拉脚本。

拟定性能目标见规格11.2，记录实际FPS、p95反馈延迟、CPU/内存和10分钟稳定性。画面通道达标后再接完整右侧面板。失败则报告具体阻塞/测量，不把轮询截图降级伪装成完整实时控制台。

### G3：动作边界接管与M5

在最终M5实现上复用pause gate和命令回执，定义普通安卓run的接管请求；pause_requested与paused分开。至少测长动作中请求暂停、最后一步请求暂停、接管与停止同时发生、人工结束与继续重复请求、旧generation消息、worker异常退出。

页面“暂停并接管”只有在worker确认安全点且旧输入排空后才能切换控制态。接管保持原runId和清理所有权，不能另建一个手动工作流抢设备。

## 6. 验证顺序与命令

每个切片执行与变更范围对应的pytest/Vitest；共享运行模型、迁移或全局组件变化后进行全量回归。新增重要测试围绕竞争、失联、未知结果、数据保留和真实输入，不写仅镜像实现细节的测试。

从仓库根目录执行，依赖当前已有环境（后续若脚本名调整同步文档）：

```sh
apps/backend/.venv/bin/python -m pytest apps/backend/tests
apps/backend/.venv/bin/ruff check apps/backend/src apps/backend/tests
apps/backend/.venv/bin/mypy apps/backend/src
npm --workspace @autoflow/desktop test -- --maxWorkers=2
npm run typecheck
npm run lint
npm run openapi:check
npm run test:scripts
npm run test:structure
npm run build
npm run backend:build
npm run package:dir
```

真实设备和视觉复验在实施阶段扩展现有 `scripts/smoke-android-management.py`，必要时增加独立视图状态验证脚本，避免用新脚本完全绕开正式应用。M4/M5真实回归以合入后的正式脚本为准，不能引用历史测试计数冒充本轮结果。

### 6.1 视觉证据

目录建议 `docs/migration/android-prototype-exact-qa/{R1,R2,R3,R4}/`，每组包含reference、actual、side-by-side、overlay、diff、viewport/state元数据。每次修复替换actual并保留差异记录。对照必须同尺寸/同状态；不能把手机/卡片/文本整块屏蔽以提高分数。

P0/P1/P2修复完才可通过；规格12.1定义的≤4px主区块/≤2px重复控件是初定验收容差，逐图记录实际测量。系统标题栏单独核对，不重复绘制OS控件。四图均通过才将 `design-qa.md` 更新为passed。

### 6.2 真机最小完整链路

1. 配置一个兼容环境，批量创建3台测试实例，记录各deviceId/容器/卷；测试重复提交和一项明确失败。
2. 以两个不同设备并行执行可重复安卓流程，第三台保持停止；向第三台分配后观察等待启动和真就绪门槛。
3. 在A请求动作结束后暂停接管，B持续运行；A执行中文/手势/APK等检查，再继续自动流程。
4. 一台持久、一台临时：终态分别验证数据保留和自动回收；接管时不提前删临时数据。
5. 注入断线/超时/暂停与停止竞争，确认未知动作不重放、占用不假释放、回收失败仍可查看和恢复。
6. 退出/重启应用，恢复查询已有状态；测试只清理本轮创建的临时资源，不删除旧Demo或正式设备。

Mac现有VM容量接近上限；实施前读真实预算，安排独立测试容量。容量不足应明确排队，不用修改用户已有容器配额、偷偷停止旧设备或假报就绪来完成验收。

## 7. 文档、提交与完成定义

- 当前只提交规格、实施计划、四张原图与索引、旧视觉结论纠正；不修改业务代码，不启动新服务，不重建App。
- 确认后每个垂直切片独立提交，提交描述明确行为；主线M5尚未提交时保持隔离，不强行合并。
- 完成时更新 `.ai/decisions`、`.ai/plans`、`.ai/sessions`、目录索引、验证记录和根目录design-qa。
- 交付报告分别列：四图还原V结果、真机功能F结果、使用入口、迁移/数据状态、未测平台。任一图遗漏主要区块或按钮无对应能力，均不能称为“一模一样的完整实现”。
- 这份计划没有把缺失功能继续延期到不确定的下一版；P0–P8共同构成本次完整还原目标。只有摄像头/环境伪装/跨主机调度等四图外能力不在范围内。
