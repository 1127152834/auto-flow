# PM9 Windows 现有文件写入后续计划

日期：2026-09-23。状态：proposed；只供选择合同，未批准实施。来源：[S4 补充提案](../specs/2026-09-23-pm9-windows-existing-file-replacement-boundary.md)、原生专项 35832925704、当前 `WorkflowArtifactStore` 与表格/Base64 调用链。

已完成且不受本计划影响：Windows 安全新文件发布、普通现有文件安全读取、绝对盘符表格新文件导出及 Job 所有权子片。既有文件覆盖/追加保持 501，`releaseAccepted=false`。

## 决策门

选择 A：保持 Windows 既有路径覆盖/追加 501，并将此限制写入产品验收。选择 B：批准版本化输出替代同路径覆盖/追加；每次写入返回新的不可变物理文件，应用中的逻辑输出引用切换到最新版本，旧文件不删除。B 会改变可见路径和“追加”含义，不能在未确认时实施。原 S4 同路径条件原子替换合同继续作为未满足项，不把 B 记为原合同的直接通过。

## 若选择 B 的垂直切片

1. 冻结契约：在现有工作流产物模型上定义逻辑输出引用、物理文件路径、预期代次、返回值和 UI 文案；明确绝对用户路径首次存在、同名重试和追加请求如何映射为新版本。现有路径字符串消费者逐一列出，未迁移的调用继续 501。
2. 先写失败断言：两个 worker 同时发布同一逻辑引用、外部进程抢占目标名、取消、登记失败、响应丢失、重启及父目录重解析点；断言不覆盖外部文件、旧版本可读且无无主临时文件。
3. 复用当前 Windows `pinned_parent`/`staged_output`/`publish` 和 SQLite 产物事实：先生成唯一新文件并登记，再用原操作身份及代次 CAS 切换逻辑引用；失败只清理由本操作创建且可证明身份的文件。不得增加第二执行器或以 `stat` 后盲替换绕过原约束。
4. 更新表格/Base64/文本输出调用与页面链接，显示实际新路径和历史版本；按后端契约生成客户端。跑真实 worker、生产 HTTP、桌面源码、Windows 原生及三平台打包链，逐项更新 251 条覆盖台账；未证实的同路径合同继续列缺口。

若用户仍要求同一路径覆盖/追加而不接受 B，需要另行证明可实现“目标身份前置条件 + 原子发布”的 Windows 原生机制后再修订本计划。当前 `ReplaceFileW` 和已实验的重命名组合没有提供该证明。
