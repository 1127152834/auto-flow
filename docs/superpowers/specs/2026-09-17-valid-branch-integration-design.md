# 有效分支整合设计

- 日期：2026-09-17
- 状态：approved
- 来源：用户要求整理、分析并将仍有效的未合并代码接入 GitHub 默认分支；2026-09-17 用户确认排除已废弃或未完成的历史检查点，并选择“能力整合 + 分支对账”方案。
- 目标分支：`codex/architecture-baseline`
- 审计基线：`f62827cb0047`

## 目标

将本地及远端侧分支中仍然有效的产品能力整合到 `codex/architecture-baseline`，保留主线较新的 Studio、迁移和共享契约，避免通过机械合并恢复已退役实现。完成后，有效分支要么成为目标分支祖先，要么具有明确的能力迁入和分支对账记录；刻意排除的归档分支继续独立保存。

## 非目标

- 不恢复已退役的旧 Studio、旧 M1–M6 工作流模型或未完成试验。
- 不把分支中的历史截图、运行日志和验证产物当作当前主线的新验收证据。
- 不重写、压平或强制推送现有侧分支。
- 不把当前主工作区的未提交 Studio 后端工作混入分支整合提交。
- 不借本次整合继续实现 PM5–PM9、Android 新功能或新的设计系统能力。

## 总体策略

采用“能力整合 + 分支对账”，而不是把所有分支直接合并进当前工作树。

1. 在当前主工作区创建保护分支 `codex/pre-branch-integration-wip-20260917`，保留所有已修改和未跟踪文件，不提交、不暂存、不清理。
2. 在独立 worktree 中检出目标分支并建立整合分支 `codex/integrate-valid-branches-20260917`。
3. 对主要且整体有效的 PM4 使用真实两父合并；冲突逐项按本设计处理。
4. 对只部分有效或已经选择性接入的 Android、UI 控件、全局表格和代理分支，先迁入经过验证的能力，再创建对账合并。对账合并保留分支祖先关系，但以已经验证的整合树为准，不重新恢复被明确舍弃的旧文件。
5. 每个批次独立提交、独立验证。后续批次不掩盖前一批失败。
6. 全量验证通过后快进目标分支并推送 GitHub。保护分支上的未提交工作保持原样，单独安排回接。

## 工作区和数据保护

当前 `codex/architecture-baseline` 工作区含大量已修改及未跟踪文件。直接切换、暂存、stash 或合并都可能改变这些内容，因此整合前只执行一次分支保护：

- 在原目录创建并切换到 `codex/pre-branch-integration-wip-20260917`；未提交文件保持字节不变。
- 记录切换前后的 `git status --short`，验证修改和未跟踪路径集合一致。
- 不对保护分支提交、清理、还原或自动格式化。
- 目标分支释放后，在新 worktree 中完成全部整合。
- 最终报告分别列出目标分支提交和仍留在保护工作区的 WIP，不能把二者混为一体。

若分支切换本身因索引或路径冲突失败，停止操作并保留原工作区，不使用强制切换、重置或清理命令。

## 批次一：PM3/PM4 项目管理能力

PM4 是 PM3 的后继，PM5 与 PM4 同一提交，因此只处理 `codex/project-management-pm4`。

需要接入的能力：

- 项目自动化配置、参数批次和资源校验。
- 批次、任务、运行证据、失败截图及恢复状态。
- 多表输入选择、原子领取、数据写入 lease 和批次调度。
- 对应 HTTP、持久化、桌面页面、测试和当前仍适用的设计/验收文档。

冲突规则：

- `application/workflows`、`providers/browser`、worker 进程和 Studio 组件以当前主线接口及行为为权威；PM4 所需项目调用通过适配当前接口完成。
- 项目自动化、项目运行和项目数据领域以 PM4 能力为基础，但要服从主线现有 workspace 隔离、命令恢复和错误呈现约束。
- Alembic 不改写历史版本；从当前唯一迁移头追加必要汇合迁移。
- OpenAPI 从最终后端路由重新生成，不手工拼接冲突后的 `generated.ts`。
- 旧工作流 fixture 和已被主线替换的旧执行器不恢复。

## 批次二：Android 管理和人工接管

Android 分支基于较早的工作流实现，存在多个 modify/delete 冲突。整合只保留独立 Android 能力：

- Android 实例、运行时资源和设备状态的领域、应用、数据库及 HTTP 边界。
- Android 管理页面、设备卡、人工会话入口和当前有效测试。
- Android 工作流接管通过主线当前的 workflow run、人工输入和生命周期契约接入。

以下内容不得恢复：

- 主线已经删除的 `workflow_schemas.py`、旧 `execution.py`、旧 `StudioPage.tsx`、旧运行 hooks 和旧节点检查器。
- 已被当前 Studio 替代的旧运行工具栏、ArtifactPanel 和运行类型。
- 与现有迁移头冲突的旧迁移编号或旧生成 API 文件。

若 Android 接管无法在不恢复旧 Studio 的前提下绑定当前运行契约，该接管入口保持禁用并记录为未接入；Android 独立管理能力仍可整合。

## 批次三：共享 UI 控件和全局表格

UI 控件分支跨越 313 个文件，不能以旧调用方覆盖当前页面。整合按控件能力执行：

- 对照当前共享组件，迁入仍缺失且有当前调用者的控件、焦点管理、OverlayHost、滚动和表单绑定行为。
- 已经存在的 token、overlay、pagination、select、modal 和 toast 以当前版本为基础，只吸收缺失测试覆盖或明确修复。
- 旧 UI Lab、旧页面批量重构和仅用于历史截图的入口不进入生产构建；仍有诊断价值且不会增加运行路径时才保留。
- 全局表格以 PM4 已整合版本为基线，对比 `d3afba68` 的表格行为，补齐当前项目数据和 Studio 表格确实缺少的密度、固定列、查询工具及可访问性行为。
- 不为了让补丁原样应用而恢复旧 `BlockFlowView`、`DebugBar`、`GlobalConfigDialog` 或 `LogPanel` 结构。

## 批次四：代理能力对账

主线已有 `c8609227` 选择性接入代理管理，并在之后加入凭据加载、远程位置和轮换控制。对账步骤：

- 按代理连接、凭据、健康检查、本地组、事务同步、ProxyPanel 映射、打包资源和桌面管理页面建立能力矩阵。
- 每项使用当前测试和实际代码证明主线已覆盖，不能仅以相似文件名判断。
- 只补主线真实缺失且仍符合当前架构的行为。
- 不用旧 `App.tsx`、旧生成类型或旧页面替换当前实现。
- 能力覆盖确认后创建对账合并，使代理来源分支不再重复出现在有效未合并清单中。

## 分支对账合并

对只部分适用的分支，对账合并必须满足以下前置条件：

1. 有逐项能力矩阵，列出迁入、主线已有、被替代和排除的内容。
2. 所有迁入代码已经在对账合并之前提交并通过目标测试。
3. 对账合并是两父提交，第一父为当前整合分支，第二父为来源分支；提交说明引用能力矩阵。
4. 对账合并后的文件树必须与合并前已经验证的整合树一致。
5. `git diff <对账合并第一父> <对账合并提交>` 必须为空。

这种提交只记录“该来源分支已完成语义处理”，不能用来掩盖未审计代码。

## 错误处理和停止条件

- 任一批次出现无法确定业务权威的冲突时，停止该批次，不猜测合并。
- 数据库出现多个未解释迁移头、降级路径断裂或历史迁移被改写时，停止整合。
- 生成类型只能由当前 OpenAPI 重新生成；生成结果与运行时路由不一致时停止。
- 工作区隔离、凭据边界、lease、CAS、命令恢复或取消语义发生回归时，不进入下一批。
- 测试失败必须定位到引入批次；不能用删除测试、放宽断言或跳过测试完成合并。

## 验证策略

每个批次至少执行：

- 相关后端单元、契约和集成测试。
- 相关桌面组件测试与领域测试。
- 类型检查和 OpenAPI 一致性检查。
- 迁移头及临时数据库升级验证；涉及数据库写入时增加重启恢复验证。

最终整合执行：

- `npm test`
- `npm run typecheck`
- `npm run lint`
- `npm run build`
- `npm run test:structure`
- `npm run test:scripts`
- `npm run openapi:check`
- 后端全量 `uv run --directory apps/backend pytest`
- 迁移唯一头、空库升级和代表性旧库升级测试
- `npm run smoke:sidecar`
- `npm run smoke:desktop`
- PM4、Android、表格和代理已有且仍适用的专项 QA 脚本

只将本轮新运行的结果作为整合通过证据。旧分支内截图和历史日志只用于理解预期。

## 提交与远端策略

- 每个能力批次形成清晰提交；冲突解决与该能力放在同一批次，避免单独的无语义“解决冲突”提交。
- 对账合并使用明确的 `merge:` 提交信息并引用审计文档。
- 全量检查通过前不更新目标分支和 GitHub 默认分支。
- 最终通过后，将 `codex/architecture-baseline` 快进到整合结果并推送 `origin`，不强制推送任何既有分支。
- 保留来源分支和两个归档检查点，便于追溯；是否后续删除由独立任务决定。

## 完成标准

- PM3/PM4、Android、共享 UI/表格和代理的有效能力均有代码或明确的主线覆盖证据。
- PM3、PM4、PM5、Android、全局表格、UI 控件和代理分支在 Git 中完成祖先或对账关系。
- 两个归档检查点仍未进入目标分支，并有文档化原因。
- 主线最新 Studio、迁移、OpenAPI、工作区隔离和安全边界没有被旧实现覆盖。
- 全量验证通过，GitHub 目标分支与本地整合提交一致。
- 原工作区的未提交修改和未跟踪文件仍完整保留在保护分支工作区。
