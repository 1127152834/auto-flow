# 参数型批次并发补充方案

日期：2026-09-26；状态：approved。2026-09-26 用户明确“开始实施”，并要求同一记录不能同时分配给两个工作流任务。
来源：用户要求并发可手填；scheduler.py、project_runs/rules.py、project_automations/rules.py 和已批准 2026-09-21-pm9-multi-run-capacity.md。

## 现状与变更

旧方案明确单参数批次最多一个活动实例。当前无数据输入时前后端强制 concurrency/maxLiveInstances 为 1，调度器等待当前任务结束再派发下一条；仅启用输入框不能实现并发。本补充仅取消该批次类型差别，不提高执行核心现有容量，不新增执行器。

- 所有自动化均可填写并发数与最大活动实例 1–100；本次启动可填写请求并发，仍取请求、保存配置及实际核心容量的最小可用额度。排队不算活动实例；等待人工、清理和归属核验仍占实例额度。
- 参数任务继续在启动事务中预建 queued CoreRun 和输入快照。scheduler 在现有锁和停止准入下派发队列，按批次执行数及同自动化跨批次活动实例数扣减额度，资源独占与核心原子容量检查继续生效。不能照搬数据批次把所有 queued Run 算作已用容量，导致参数队列自锁。
- 失败继续开关只决定是否派发后续任务。关闭时，已运行的其他任务允许收尾，尚未运行的任务取消；用户主动停止仍走既有取消/强停路径。默认继续只影响新自动化，不改旧配置或已冻结批次。
- 浏览器实例仍按任务隔离；同一任务内相同配置共用浏览器。没有工作流显式保存时清理临时实例，不删除历史持久环境，不改变现有显式保存行为。本轮不设计未来专用保存节点。

## 实施切片与验证

1. 前后端校验允许参数批次合法 1–100 值；自动化编辑、移除输入和启动弹窗保留手填值、取消重置和非法草稿阻止提交。更新已有测试而非另起表单体系。
2. scheduler 复用核心 dispatch/容量和资源租约，以两个等待事件证明同批次两个 Run 真正重叠、第三个排队、释放后补位。补请求/配置/跨批次实例上限、停止准入、失败继续开关、人工等待和核验占用；保留默认 1 的串行回归。
3. 运行相关 project_automations/project_runs 契约与集成测试、前端两领域测试、lint、类型和构建。真实 worker 场景验证相同模板的不同任务隔离、取消一方不影响另一方。没有通过前不开放参数并发，不改变 PM9 releaseAccepted=false。
