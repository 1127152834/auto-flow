# M3 吞吐与性能 设计规格

- 日期：2026-09-30；修订：r2；状态：proposed（按用户已确认的评审方向修订，未实施；开工门槛见总纲）
- 总纲：[整改里程碑总纲](2026-09-30-remediation-roadmap.md)；对应整改方案 B2、C3、C5（完整形态）、D2、E1、E2、E3、E4
- 前置：M2A/M2B 已退出并建立 native-batch-v1 基线；M2C 不阻塞。perIdentity 不属于本阶段。
- 实施计划：[M3 实施计划](../plans/2026-09-30-remediation-m3-throughput.md)（任务级）

## 1. 结论

M3 把规模从"几十行"推到"万级稳定"：领取变成索引查询，普通日志不再逐条同步提交，worker 进程和浏览器会话可以复用，登录环境只保存必要数据并定期清理。

## 2. 背景（M0 基线与评审实测）

- 1 万行表单次领取 2.0–2.6 秒；领取在线程中执行后主循环最大延迟仍约 130 毫秒（M1 原型实测，来自 GIL）。
- G4 每节点 5 个事件，每个事件一次同步提交（WAL 前 p50 4.1 毫秒，WAL 后约 1.4 毫秒），即每节点约 7–20 毫秒框架开销。
- 每个任务新起 Python 进程（启动超时 90 秒）和浏览器。
- 环境恢复与保存整目录复制、全量 SHA-256，没有清理旧代次。

## 3. 目标与非目标

**目标**：第6节性能预算按固定负载/平台验证；先SQL下推和事件批量，再按实测决定写线程、进程池与存储优化。每项独立前后对照，不把全部重构当作获得收益的先验条件。

**非目标**：身份、perIdentity会话与代理粘性（M4）；执行栈合并（M6）；分布式或多机执行。

## 4. 需求

| 编号 | 需求 |
| --- | --- |
| R3-01 | 领取SQL下推：筛选、排序、台账与完整处理单位作用域匹配；优先复用现有独立状态列/可索引字段。确需动态字段索引时使用record_index并与记录写入同事务维护，定义typed值/缺失/null/排序规则一致性；不同时要求动态生成列和索引副本两套实现。无法下推时明确扫描范围，性能目标不伪称覆盖全扫描。 |
| R3-02 | 候选预取：一次查询取 并发数 × 4 条候选，逐条用条件插入抢占租约；租约表对 `lease_key` 建部分唯一索引（仅活动租约），冲突即跳过下一条。租约判断改为索引查询，不再加载全库租约。 |
| R3-03 | 先测事件批量和SQL下推后的锁等待/主循环延迟。仍有瓶颈才实施单一DatabaseWriter；按测量报告确认后迁移写路径，禁止事务内等待另一排队写事务。队列有界、有背压/超时和关闭排空，不在持有执行锁时等队列；所有Session在所属线程创建与释放。未启用时保留既有短事务，记录理由，不伪称已交付全局写线程。 |
| R3-04 | 状态事件（外部副作用发出前的重放门禁、数据写回、环境保存、End、人工检查点、终态、产物登记）同步提交与ACK；过程日志/进度可200ms或100条批量。节点状态若用于恢复/副作用判断就不是可丢过程事件。为缓冲和状态消息规定单调序号/水位、去重、越序等待和终态flush，崩溃最多丢最后一批非权威过程信息，不丢业务事实。 |
| R3-05 | 仅在日志容量/查询测量证明必要时迁JSONL，数据库保留索引/摘要；明确文件写入与索引崩溃一致性、丢响应重放和恢复扫描。默认14天保留可配置，活跃/待核实运行和被保留证据引用的日志不自动清理。 |
| R3-06 | 冷启动测量显示Python进程成本显著时引入worker池；大小不超过存活上限，采用按需预热而非启动即占满。每50个任务或RSS阈值回收，阈值在本阶段步骤细化时据基准确定。复用前清空运行上下文/凭据/代理/回调，执行代次、撤权与原生归属仍验证；输入事件驱动替代忙等。 |
| R3-07 | M3只提供perTask默认与受限pool无登录采集；perIdentity在M4实现，M3不能先暴露不可用选项。pool仅复用浏览器进程，任务使用新的隔离上下文；必须验证Cookie、Local/SessionStorage、IndexedDB、ServiceWorker与授权状态不串任务。内核不支持所需隔离时保留perTask并记录限制，不以清Cookie冒充隔离。临时身份新种子分配留M4，不为pool制造临时identity_id。 |
| R3-08 | 多批次公平调度：批次优先级（高 / 普通 / 低），同优先级按轮转分配名额；每个批次可设自己的并发上限。 |
| R3-09 | 环境优化逐项测量；目录位于infrastructure/filesystem/environment_store.py，平台复制通过已有平台适配边界。缓存排除可按环境覆盖；不可变代次不得硬链接到可写运行目录。清单哈希只能作为变化检测，不能替代需完整性证明的摘要；关键身份/登录数据保留内容校验。clonefile/块克隆仅经原生平台验证后启用，其他环境继续正确的复制路径。 |
| R3-10 | 保留最近3个未被引用的历史代次之外，还必须保留当前代次、活动实例/冻结Task/未完成保存或关联命令/回退引用的代次。候选清理先标记、重新查引用、再删除，恢复与保留建立引用须与清理互斥，禁止只按目录年龄判断孤儿。磁盘指标分别展示可回收和被引用保留部分。 |

## 5. 设计要点

- 动态索引若采用record_index，键必须包含M2定义的完整记录作用域；每条更新/导入/删除/代次切换同步维护，并有可重建及一致性检查。SQL翻译留infrastructure/database，不让domain依赖SQLAlchemy或数据库方言。
- 事件分级需要修改 worker 协议（`protocolVersion: 2`）：新增 `eventBatch` 消息；主服务对 v1 worker 保持兼容一个版本。
- 会话复用下，浏览器生命周期与任务解耦：`WorkflowBrowserResources` 增加"租借 / 归还"语义；执行代次撤权时强制关闭该浏览器而不是归还。
- 性能验证全部通过 M0 基准扩展：`bench_claims` 加 100,000 行；新增 `bench_first_node_latency`（领取到首节点开始）。

## 6. 验收标准（E4 预算）

| 编号 | 验收 |
| --- | --- |
| AC3-01 | 领取一个任务（100,000 行表）< 20 毫秒（bench_claims，CI macOS）。 |
| AC3-02 | 领取期间及 G2 全程主循环延迟 p99 < 50 毫秒。 |
| AC3-03 | G4 框架开销 < 5 毫秒 / 节点（含事件持久化）。 |
| AC3-04 | 从领取到首节点开始：池中有空闲 worker、新浏览器 < 3 秒；复用会话 < 300 毫秒。 |
| AC3-05 | native-batch-v1固定硬件/内核/数据/故障/并发、至少5次采样，目标成功唯一行吞吐中位数≥M2B基线5倍，失败/unknown不回退；比较策略变化明确记录。未达标如实记录并评审调整，不用M0不同口径或重复任务数当分母。 |
| AC3-06 | 固定环境夹具恢复+保存目标<2秒；无额外保留引用时100次运行后占用≤单环境×4；有长期引用时允许超出但不得误删，逐项报告占用原因。 |
| AC3-07 | 并发 1,000 次领取（随机筛选、随机并发）的随机化测试：不重复、不遗漏、不死循环。 |
| AC3-08 | worker在过程批次发送前、发送后未ACK、外部动作前后、终态flush时被杀：最多丢最后非权威过程批，副作用门禁/状态事件完整，重复序号不重复写入。 |

## 7. 风险

| 风险 | 应对 |
| --- | --- |
| 排除缓存导致个别网站登录失效 | 排除列表可按环境覆盖；M4 的 G1 验证登录保持 |
| 会话复用串数据 | pool只限无登录；新隔离上下文及多存储/授权隔离通过后才能启用 |
| 写线程成为瓶颈 | 批量写入；监控队列长度，超过阈值记警告 |
| 协议升级 | v1/v2 共存一个版本；契约测试覆盖两种 |
